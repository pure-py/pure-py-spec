\section{Introduction}
\label{sec:introduction}

Scientific results are increasingly computed by programs written with, or generated outright by, AI coding
tools. Most new users of GitHub now try a coding assistant within their first
week~\cite{github2025}, and the reliability of generated scientific code is an open question with benchmarks
of its own~\cite{tian2024,chen2025,siegel2024}. Whatever the success rate of the current models, scientific
results that rest on generated programs need assurance that the programs work as intended. Verification
against a formal specification provides such assurance in principle, but a generated program is accepted on
the strength of its output, because the scientist who asked for it rarely has a specification to verify it
against. More broadly, assurance that AI systems work as intended is now a stated priority of UK
policy~\cite{clifford2025,dbt2025}.

Python is the usual language for this code. Python is the most used language on GitHub in AI and data
science~\cite{github2025}, and scientific computing is among the fields driving its use~\cite{github2024}.
AI coding tools favour Python when a task leaves the choice open, choosing it in most cases even where another
language would serve better~\cite{twist2026}, and most of the code-generation benchmarks surveyed by
\citet{siddiq2024} are in Python. They also generate Python more
accurately than languages with less training data, such as OCaml and Racket~\cite{cassano2023}. Fine-tuning
closes the gap only in part~\cite{cassano2024}.

Assurance is hard to obtain for Python. The language has not been given an official formal semantics, and the
formalisations constructed by researchers~\cite{guth2013,kohl2021,politz2013,melancon2023} model the behaviour
of the full language rather than delimiting a subset within which reasoning is tractable. Even given a
semantics, three aspects of the language make Python programs hard to reason about. Under mutable state, the
value of a variable depends on every assignment that may run before a use. Under dynamic binding, the referent
of a name is fixed only when the name is evaluated. Under load-order dependence, the meaning of a qualified
name can depend on which modules have loaded elsewhere in the program (\secref{no-load-dependent}).

\PurePy is a statically typed, immutable subset of Python with a formal static and dynamic semantics. Every
well-formed \PurePy program is a valid Python program, and every terminating run with defined behaviour under \PurePy
produces the same result under Python. This guarantee, which we call agreement, is stated in
\secref{python-compatibility} and tested by a conformance suite on CPython, GraalPy and Pyodide
(\secref{reference-implementation}). The guarantee is unproven (\secref{agreement}); the metatheory of
\secref{metatheory} concerns the well-formedness of environments. Every function and dataclass field is
annotated, so that types are given rather than inferred. The type system accepts only programs accepted by
mypy, so that \PurePy programs are checked by the toolchain already used by Python programmers. \PurePy
excludes Python idioms that would break purity, compatibility with mypy or deterministic failure, under which
a failing program fails in the same way under every implementation (\secref{purity}). Several of the excluded
idioms, such as wildcard imports, are also discouraged by PEP 8,\footnote{\url{https://peps.python.org/pep-0008/}}
so the exclusions partly follow established Python practice and the subset is lightly opinionated as well as
pure.

We take the position that machine-generated code changes the economics of language design. Features that
spare human authors effort, such as mutation in place, implicit coercion and late binding, have a cost in
reasoning that is paid by whoever must trust the result. When the author is a machine, the effort saved is worth
little and the cost remains, so strictness and formal guarantees gain value. A stricter language that departs
from Python's syntax, however, forfeits Python's training data and benchmarks. A subset of Python keeps the
training data and benchmarks, because its programs are Python programs. The evaluation of \secref{evaluation}
measures the cost of this strictness to a code generator. It compares code generation into \PurePy with
generation into Python and into OCaml on standard benchmarks, and reports how often the type checker rejects a
first attempt, how many rounds a generator needs to reach a well-formed program and how often the final program
passes the tests.

\PurePy is also intended as a foundation for programming-language research on generated code, in two roles.
In the first, a research language compiles to \PurePy, so that the properties enforced by its type system
hold by construction for the compiled programs and its remaining guarantees can be stated against the \PurePy
semantics. The two case studies of \secref{case-studies}, a language with units of measure and a language
with provenance tracking, take this role, compiling to \PurePy by type erasure and by desugaring respectively.
In the second, analyses grounded in the \PurePy semantics check generated programs in place, with no
translation between the checked program and the program run by the scientist. \PurePy does not yet cover the
array and dataframe libraries on which scientific computing in Python rests; \secref{conclusion} discusses
pure counterparts.

\subsection{Contributions}

After an overview of the design and its exclusions (\secref{overview}), we make the following contributions:
\begin{itemize}
\item a definition of \PurePy as a versioned standard\footnote{This paper describes version
\versionstring{} of the \PurePy language specification, which \specificationavailability. Figures and
sections of the specification are numbered with the prefix \specmark, as in \specfigref{precedence}.}, with a formal
grammar (\secref{syntax}), a type system (\secref{well-formedness}) and an operational semantics designed so
that every terminating run with defined behaviour under \PurePy{} produces the same result under Python
(\secref{operational-semantics});
\item a reference type checker that decides well-formedness, and a conformance suite that tests agreement on
CPython, GraalPy and Pyodide (\secref{reference-implementation});
\item two research languages built on \PurePy, one of which extends the core language with partial application
and piecewise function definitions (\secref{case-studies});
\item an evaluation of AI code generation into \PurePy, compared with generation into Python and OCaml, on standard benchmarks (\secref{evaluation}).
\end{itemize}
\secref{related-work} discusses related work and \secref{conclusion} concludes.

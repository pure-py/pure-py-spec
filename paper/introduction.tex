\section{Introduction}
\label{sec:introduction}

\begin{DeletedBlock}
Python is among the most widely used languages in scientific computing, data analysis, and teaching, valued for
an accessible surface syntax and a large ecosystem. That reach comes with a large and permissive language.
Programs mutate state freely, depend on side effects and dynamic binding, and allow many implicit coercions, so
they can be hard to reason about, hard to reproduce, and hard to target with formal tools or with
implementations other than the reference interpreter. A researcher in programming languages or in pedagogy who
wants a well-behaved functional language faces a trade-off: such a language is easy to reason about but
unfamiliar, whereas Python is familiar but unruly.

\PurePy carves out a pure, side-effect-free subset of Python that is well-behaved and easy to reason about, yet
remains ordinary Python. Every well-formed \PurePy program is valid Python, and when \PurePy gives a run a
result, a standard interpreter gives the same one, so one artifact serves two roles: a program that a scientist can run today, and a
common target that a research language or tool can produce and consume. Purity makes programs referentially
transparent, deterministic, and reproducible, the properties that scientific computing and formal reasoning
both want.

This paper defines \PurePy as a versioned formal standard\footnote{This paper describes version
\versionstring{} of the \PurePy language specification, which \specificationavailability.}: a formal grammar, a type system that accepts only
programs accepted by mypy, and an operational semantics that agrees with Python on every run that it defines. A reference checker decides well-formedness, and a conformance test suite exercises the
standard against CPython,  GraalPy, and Pyodide. The guarantee is precise: well-formedness is decidable, and
\PurePy either gives a run Python's result or gives it no result at all.

The design is deliberately conservative. Rather than reconstruct Python's full behaviour, \PurePy chooses a
simple, well-behaved core and excludes the idioms that would break it, among them mutable state, effectful
control, implicit coercions, and constructs whose meaning depends on module load order
(\secref{overview}). The standard is versioned, so the subset can grow as features earn their place
without disturbing programs written against an earlier version.

\PurePy is aimed first at researchers in programming languages and in pedagogy, and is intended to grow into a
common language for scientific computing, supporting portable applications in modelling, data processing,
analysis, and visualisation. Because every \PurePy program is also a Python program, adopting it costs nothing
at the surface, and a research language that targets \PurePy inherits a large and familiar runtime.
\end{DeletedBlock}

\begin{AddedBlock}
Scientific results are increasingly computed by programs written with AI coding assistants, or generated
outright by language models. Most new users of GitHub now try a coding assistant within their first
week~\cite{github2025}, and benchmarks of research coding tasks curated by scientists~\cite{tian2024,chen2025}
and of the reproduction of published computational results~\cite{siegel2024} report that current models and
agents fail on most tasks. A scientific result that rests on a generated program therefore needs assurance
that the program works as intended, and assurance that AI systems work as intended is now a stated priority
of UK policy~\cite{clifford2025,dbt2025}. Verification against a formal specification provides such assurance
in principle, but the scientist who asks for a program rarely has a specification to verify it against.

Most of this code is Python. Python is the most used language on GitHub for data science and scientific
computing~\cite{github2024,github2025}, language models choose it by default when a task leaves the choice
open~\cite{twist2026}, and most code-generation benchmarks are written in it~\cite{siddiq2024}. Models also
generate Python more accurately than languages with less training data, such as OCaml and Racket, a gap
closed only in part by fine-tuning~\cite{cassano2023,cassano2024}.

Python resists assurance. The language has no official formal semantics, and the formalisations constructed
by researchers~\cite{guth2013,kohl2021,politz2013,melancon2023} model the behaviour of the full language
rather than delimiting a subset within which reasoning is tractable. Even given a semantics, three features
make Python programs hard to reason about. Under mutable state, the value of a variable depends on every
assignment that may run before a use. Under dynamic binding, the referent of a name is fixed only when the
name is evaluated. Under load-order dependence, the meaning of a qualified name can depend on which modules
have loaded elsewhere in the program (\secref{no-load-dependent}).

\PurePy is a statically typed, immutable subset of Python with a formal static and dynamic semantics. Every
well-formed \PurePy program is a valid Python program, and every run given a result by the \PurePy semantics
produces the same result under Python, a guarantee made precise in \secref{python-compatibility} and tested
by a conformance suite on CPython, GraalPy and Pyodide (\secref{reference-implementation}). The guarantee is a
conjecture rather than a theorem (\secref{agreement}); the proven metatheory concerns the well-formedness of
environments (\secref{metatheory}). Every function and dataclass field is annotated, so that types are given
rather than inferred, and the type system accepts only programs accepted by mypy, so that a \PurePy program
is checked by the toolchain already used by Python programmers. \PurePy excludes a Python idiom when the
idiom would break purity, compatibility with mypy or the determinism of failure (\secref{purity}). Several of
the excluded idioms, such as wildcard imports, are also discouraged by Python's own style guide, so the subset
is lightly opinionated as well as pure.

We take the position that machine-generated code changes the economics of language design. Features that
spare a human author effort, such as mutation in place, implicit coercion and late binding, have a cost in
reasoning, paid by whoever must trust the result. When the author is a model, the effort saved is worth
little and the cost remains, so strictness and formal guarantees gain value. A stricter language that departs
from Python's syntax, however, forfeits Python's training data and benchmarks, whereas a subset of Python
keeps them, because its programs are Python programs. The evaluation of \secref{evaluation} tests this
position by comparing code generation into \PurePy with generation into Python and into OCaml on standard
benchmarks, measuring how often the checker rejects a first attempt, how many rounds a model needs to reach a
well-formed program, and how often the final program passes the tests.

\PurePy is also intended as a baseline for programming-language research on generated code, in two roles. A
research language built on \PurePy inherits a semantics against which its guarantees can be stated, so that
its programs are correct by construction with respect to that semantics. The two case studies of
\secref{case-studies}, a language with units of measure and a language with provenance tracking, take this
role, compiling to \PurePy by type erasure and by desugaring respectively. Alternatively, an analysis grounded
in the semantics checks a generated \PurePy program in place, with no translation between the checked program
and the program run by the scientist. \PurePy does not yet cover the array and dataframe libraries on which
scientific computing in Python rests; \secref{conclusion} discusses pure counterparts.
\end{AddedBlock}

\subsection{Contributions}

\begin{DeletedBlock}
After setting out the problem addressed by \PurePy in \secref{overview}, we make the following
contributions:
\begin{itemize}
\item a definition of \PurePy as a versioned standard, with a formal grammar, a type system
(\secref{well-formedness}) and an operational semantics that agrees with Python on
every run that it defines (\secref{operational-semantics});
\item a reference checker that decides well-formedness, validated by a conformance test suite
exercised on CPython,  GraalPy, and Pyodide (\secref{reference-implementation});
\item conservative extensions to the core language, including partial application and piecewise function
definitions (\secref{extensions});
\item case studies that use \PurePy as a common functional language (\secref{case-studies});
\item an experimental evaluation of how well AI agents generate \PurePy and translate existing Python into it
(\secref{evaluation}).
\end{itemize}
\secref{related-work} summarises related efforts, and \secref{conclusion} presents our conclusions
and discusses future work.
\end{DeletedBlock}

\section{Experimental evaluation}
\label{sec:evaluation}

We evaluate empirically the suitability of \PurePy as a target language for generated code, with a language
model as the code generator. The evaluation asks three research questions.
\begin{enumerate}[label=\textbf{RQ\arabic*},ref=RQ\arabic*,leftmargin=*]
\item\label{rq:effort} How much effort does a \PurePy solution take to generate, compared with Python?
\item\label{rq:solutions} How do \PurePy solutions compare with Python solutions in correctness and size?
\item\label{rq:translation} How well does a model translate existing Python into \PurePy, and which restrictions make
translation difficult?
\end{enumerate}

\subsection{Experimental setup}
\label{sec:evaluation-setup}

The benchmarks are three standard Python code-generation benchmarks: HumanEval+ and MBPP+~\cite{liu2023},
which extend HumanEval~\cite{chen2021} and MBPP~\cite{austin2021} with many more tests per problem, and
LiveCodeBench~\cite{jain2025}, which has an official harness for Python solutions. HumanEval problems
are small functions over the standard library, so most fall within the \PurePy subset.

A language model is given the same problems from these benchmarks in each of the settings listed in
\tabref{evaluation-settings}, with equivalent documentation in each. For each problem and setting, the
procedure is as follows.
\begin{enumerate}
\item Prompt model with problem and documentation for setting
\item Extract program from response
\item Check program statically, except in Python setting
\item If static check rejects program and repair rounds remain, return diagnostics to model and continue from step 2
\item Run final program against benchmark's official tests
\item Record outcome of every round
\end{enumerate}
The model never sees test outcomes. The benchmark's tests run unchanged against \PurePy solutions under CPython,
because every \PurePy program is a Python program.

Some problems depend on Python features which are compatible with the design of \PurePy but do not yet form part
of the specification. If the inputs or expected outputs in the tests of a problem include values of a type
outside the specification, for example sets, complex numbers or dictionaries with integer keys, no \PurePy
solution exists, and the problem is excluded. If a solution uses another feature outside the specification, for
example the module \pyinline{re} or the built-in \pyinline{sum}, the problem is kept, because a solution without
the feature may exist, and the resulting rejections are counted separately from rejections caused by the
restrictions of \PurePy. Without loops, a \PurePy program must use recursion to accumulate a result over its
input, since comprehensions only map and filter. CPython has no tail-call optimisation, so recursion over large
inputs can exceed its recursion limit; such failures count against \PurePy and are reported as a category of
their own.

\subsection{Effort of generating \PurePy solutions\texorpdfstring{ (\rqref{effort})}{}}
\label{sec:evaluation-effort}

\rqref{effort} asks how much effort a \PurePy solution takes to generate, compared with Python. Effort is
measured in rejections, repair rounds and tokens; Python solutions are not checked and so take one round. Over
all rounds, we count rejections by the rule named in each diagnostic. For each rejection, we record whether the
next round removes the violation, and the number of rounds to acceptance. We also count the input and output
tokens per problem, up to acceptance or the budget, in \PurePy and in Python.

\subsection{Correctness and size of \PurePy solutions\texorpdfstring{ (\rqref{solutions})}{}}
\label{sec:evaluation-solutions}

\rqref{solutions} asks how \PurePy solutions compare with Python solutions in correctness and size. For
correctness, we compare the pass rate of the final program in \PurePy and in Python. A third setting, unchecked
\PurePy, keeps the grammar of \PurePy, with annotations optional, and drops the well-formedness rules. Comparing
unchecked \PurePy with \PurePy measures the effect of the well-formedness rules, and comparing it with Python
measures the effect of the grammar. \figref{evaluation-generation} reports the pass rates of the \PurePy and
Python settings. For size, we compare the final \PurePy program, in non-blank lines and in tokens, with the
model's Python solution and, for HumanEval+ and MBPP+, with the benchmark's reference solution.

\subsection{Translation of existing Python\texorpdfstring{ (\rqref{translation})}{}}
\label{sec:evaluation-translating}

\rqref{translation} asks how well a model translates existing Python programs into \PurePy, and which
restrictions make translation difficult. The model is given the benchmark's reference solution to each problem
and asked for a \PurePy version, under the same loop as for generation. A translation succeeds if the type
checker accepts it and it passes the tests. We report how often translation succeeds, and classify each
rejection by the rule named in its diagnostic. The rules are grouped into restrictions of \PurePy and features
which do not yet form part of the specification, such as sets and library modules. \todo{Unclear whether this

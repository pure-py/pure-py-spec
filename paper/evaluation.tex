\section{Experimental evaluation}
\label{sec:evaluation}

We evaluate empirically the suitability of \PurePy as a target language for generated code, with a language
model as the code generator. The evaluation asks four research questions.
\begin{description}
\item[RQ1] How does \PurePy compare with other functional languages as a target for code generation?
\item[RQ2] What do the restrictions of \PurePy cost the generator, in rejections and repair rounds?
\item[RQ3] How do the restrictions of \PurePy affect the generated program, in correctness and in length?
\item[RQ4] How well does a model translate existing Python into \PurePy?
\end{description}
\secref{evaluation-setup} describes the setup shared by the four questions, and
\secref{evaluation-languages} to \secref{evaluation-translating} take the questions in turn.

\subsection{Experimental setup}
\label{sec:evaluation-setup}

A model is given the same problems under several conditions, with equivalent documentation for each.
\tabref{evaluation-conditions} lists the conditions and the questions which use them. For each problem and
condition, the procedure is as follows.
\begin{enumerate}
\item The model is given the problem and the documentation for the condition.
\item The program is extracted from the answer.
\item The program is checked statically, unless the condition is Python.
\item If the check rejects the program and repair rounds remain, the diagnostics are returned to the model, which
answers again, and the procedure continues from step 2.
\item The final program is run against the benchmark's official tests.
\item The outcome of every round is recorded.
\end{enumerate}
Test outcomes are not fed back, so a pass measures generation from the problem statement and the checker's
diagnostics alone. A \PurePy answer is a Python program, so the benchmark's Python tests run unchanged against it
under CPython.

The benchmarks are HumanEval+ and MBPP+~\cite{liu2023}, which extend HumanEval~\cite{chen2021} and
MBPP~\cite{austin2021} with many more tests per problem, and LiveCodeBench~\cite{jain2025}. HumanEval problems
are small functions over the standard library, so most fall within the \PurePy subset. The self-repair
scenario of LiveCodeBench, in which the model fixes a solution given failing test output, is the nearest
precedent for the repair loop.

The evaluation pipeline in \filename{evaluation/} implements this procedure for the \PurePy and Python
conditions, and produces \figref{evaluation-generation} from the recorded outcomes. The

\subsection{Comparison with other functional languages}
\label{sec:evaluation-languages}

RQ1 asks how \PurePy compares with other functional languages as a target for code generation. Language models generate Python more accurately than languages with less training data.
MultiPL-T~\cite{cassano2024} measures how much worse models do in OCaml and Racket, and closes part of the gap
by fine-tuning on Python programs translated into those languages. Because \PurePy programs are Python
programs, a model trained on Python is already trained on \PurePy, and we conjecture that this spares \PurePy
the gap without fine-tuning. The comparison language is OCaml, restricted to its pure subset, with no references
or mutable fields, so that it differs from \PurePy mainly in syntax; MultiPL-E~\cite{cassano2023} provides the
benchmarks translated into OCaml. We compare \PurePy with OCaml on how often the static check accepts the first
attempt, how often the final program passes the tests, and the number of rounds to an accepted program. A clear
gap in \PurePy's favour would support the conjecture; a small gap would mean that the argument needs rethinking.

\subsection{Cost of the restrictions to the generator}
\label{sec:evaluation-cost}

RQ2 asks what the restrictions of \PurePy cost the generator. Over all rounds, we count rejections per
forbidden feature. Each diagnostic of the checker is named after the rule it enforces, so a rejection is
classified by its diagnostic. For each rejection, we record whether the next round clears the feature, and
the number of rounds to acceptance. The restrictions are not a barrier if violations are rare and are cleared
in a round or two from the diagnostic alone.

\subsection{Effect of the restrictions on the program}
\label{sec:evaluation-effect}

RQ3 asks how the restrictions of \PurePy affect the generated program, in its correctness and in its length.
For correctness, we compare the pass rate of the final program in \PurePy and in Python; the gap is the effect
of the restrictions as a whole. A third condition, unchecked \PurePy, keeps the grammar of \PurePy, with
annotations optional, and drops the well-formedness rules, so an answer is checked for syntax only and run by
CPython. Comparing \PurePy with unchecked \PurePy measures the effect of the well-formedness rules, and
comparing unchecked \PurePy with Python measures the effect of the grammar. Types may catch errors otherwise
revealed only by the tests, and the model may write better code when it must state types. RQ2 measures the
cost of the restrictions in rejections and rounds, and RQ3 their benefit in correctness.
\figref{evaluation-generation} reports the pass rates of the \PurePy and Python conditions.

For length, a program confined to a functional style may be more concise, although a shorter program is not
necessarily a better one. We compare the length of the final \PurePy program, in non-blank lines and in
tokens, with the model's Python answer to the same problem, which holds the author constant, and with the
benchmark's reference solution, which HumanEval+ and MBPP+ provide but LiveCodeBench lacks.

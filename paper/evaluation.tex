\section{Experimental evaluation}
\label{sec:evaluation}

We evaluate empirically the suitability of \PurePy as a target language for generated code, with a language
model as the code generator. The evaluation asks four research questions.
\begin{description}
\item[RQ1] How does the familiarity of Python syntax affect the difficulty of generating functional programs?
\item[RQ2] What do the restrictions of \PurePy cost the generator, in rejections, repair rounds and tokens?
\item[RQ3] How do the restrictions of \PurePy affect the generated program, in correctness and in length?
\item[RQ4] How well does a model translate existing Python into \PurePy, and which restrictions make translation
difficult?
\end{description}
\secref{evaluation-setup} describes the setup shared by the four questions, and
\secref{evaluation-syntax} to \secref{evaluation-translating} take the questions in turn.

\subsection{Experimental setup}
\label{sec:evaluation-setup}

A model is given the same problems in each of the settings listed in \tabref{evaluation-settings}, with
equivalent documentation in each. For each problem and setting, the procedure is as follows.
\begin{enumerate}
\item Prompt model with problem and documentation for setting
\item Extract program from answer
\item Check program statically, except in Python setting
\item If static check rejects program and repair rounds remain, return diagnostics to model and continue from step 2
\item Run final program against benchmark's official tests
\item Record outcome of every round
\end{enumerate}
Test outcomes are not fed back, so a pass measures generation from the problem statement and the checker's
diagnostics alone. A \PurePy answer is a Python program, so the benchmark's Python tests run unchanged against it
under CPython.

The benchmarks are HumanEval+ and MBPP+~\cite{liu2023}, which extend HumanEval~\cite{chen2021} and
MBPP~\cite{austin2021} with many more tests per problem, and LiveCodeBench~\cite{jain2025}. HumanEval problems
are small functions over the standard library, so most fall within the \PurePy subset. The self-repair
scenario of LiveCodeBench, in which the model fixes a solution given failing test output, is the nearest
precedent for the repair loop.

Some problems have no \PurePy solution, or only one which is hard to find, for reasons unrelated to the
restrictions of \PurePy. Their tests may pass sets or dictionaries with non-string keys, which have no type in
the current version of \PurePy; a natural solution may need a library module such as \pyinline{re}, which the
current version lacks; or recursion over large inputs may exceed the recursion limit of CPython. RQ1 to RQ3
therefore use only the problems with a known \PurePy solution, namely those with a reference solution translated
successfully in RQ4. The translations of RQ4 run first.

\subsection{Familiarity of Python syntax (RQ1)}
\label{sec:evaluation-syntax}

Language models generate Python more accurately than languages with less training
data~\cite{cassano2023,cassano2024}. RQ1 asks how the familiarity of Python syntax affects the difficulty of
generating functional programs. To separate familiarity from other differences between languages, we
compare \PurePy in Python syntax with \PurePy in an ML-style syntax. The two share the abstract syntax, type
checker, documentation and tests; programs, signatures, examples and diagnostics are printed in the syntax of
the setting, and a program in ML-style syntax is printed as Python for testing. Difficulty is measured by
first-attempt acceptance, and by the rounds and tokens to a program which is accepted by the type checker and
passes the tests.

\subsection{Cost of the restrictions to the generator (RQ2)}
\label{sec:evaluation-cost}

RQ2 asks what the restrictions of \PurePy cost the generator. Over all rounds, we count rejections by the rule
named in each diagnostic. For each rejection, we record whether the next round removes the violation, and the
number of rounds to acceptance. We also count the input and output tokens per problem, up to acceptance or the
budget, in \PurePy and in Python.

\subsection{Effect of the restrictions on the program (RQ3)}
\label{sec:evaluation-effect}

RQ3 asks how the restrictions of \PurePy affect the generated program, in its correctness and in its length.
For correctness, we compare the pass rate of the final program in \PurePy and in Python. A third setting,
unchecked \PurePy, keeps the grammar of \PurePy, with annotations optional, and drops the well-formedness rules.
Comparing unchecked \PurePy with \PurePy measures the effect of the well-formedness rules, and comparing it with
Python measures the effect of the grammar.
\figref{evaluation-generation} reports the pass rates of the \PurePy and Python settings. For length, we
compare the final \PurePy program, in non-blank lines and in tokens, with the model's Python answer and, for
HumanEval+ and MBPP+, with the benchmark's reference solution.

\subsection{Translation of existing Python (RQ4)}
\label{sec:evaluation-translating}

RQ4 asks how well a model translates existing Python programs into \PurePy, and which restrictions make
translation difficult. The model is given the benchmark's reference solution to each problem and asked for a
\PurePy version, under the same loop as for generation. A translation succeeds if the type checker accepts it
and it passes the tests. We report how often translation succeeds, and classify each rejection by the rule
named in its diagnostic. The rules are grouped into the restrictions of \PurePy and the features missing from its
current version, such as sets and library modules. \todo{Unclear whether this question can be answered without libraries being part of
the specification.}

\subsection{Purity}
\label{sec:purity}

\PurePy is pure in the senses that matter for reasoning. Every name has a unique lexical scope. A variable,
once definitely assigned, denotes a fixed value. The members of a module are fixed once the module has loaded.
There is no mutation, nor can evaluation order change the meaning of a name. Python programs in general do not
satisfy these properties, and \PurePy characterises a large subset of Python within which all of them hold.

\PurePy is not pure in the stronger sense of guaranteeing that every program terminates with a unique value: as in
Haskell, a program may fail to terminate, or abort with an error such as division by zero. Errors of different kinds
are reported differently, so a program with two possible failures reveals which it reaches first. The order of
evaluation, including the order in which modules load, is therefore part of the semantics, and a failing program fails
in the same way under every implementation (\secref{no-load-dependent}). \PurePy also has \pyinline{print},
following Python, as Haskell has \pyinline{trace}; printing reports on a computation without influencing its result.

\subsubsection{Mutable state}
\label{sec:no-mutable-state}
\label{sec:local-assignment}

A variable in \PurePy is introduced by a declaration, or as a parameter, imported name, pattern variable
or generator variable; a declaration is a type annotation such as \pyinline{x: int}, a form allowed in Python since
version 3.6 (PEP 526\footnote{\url{https://peps.python.org/pep-0526/}}). \replaced{An assignment never introduces a variable
or reassigns one: a variable may be assigned only where no path has assigned it already, either in its declaration
or afterwards, and may be referenced only where an assignment covers every path to the reference, similar to how ``blank
finals'' are treated in Java~\cite[\S16]{gosling2025}. This discipline of \emph{definite assignment} is enforced
statically (\secref{well-formedness-statements}): after a conditional, a variable is definitely assigned only if each
branch either assigns it or definitely returns, and is otherwise possibly unassigned. Branch-local variables are
therefore permitted, but using one after the conditional is not, nor is completing a partial assignment:}{A variable is assigned at most once on any path, either in its declaration or afterwards, and an
assignment never introduces a variable nor reassigns one (\secref{local-assignment}). }

\begin{AddedBlock}
\begin{python}
def foo(b: bool) -> int:
    x: int
    if b:
        x = 3
        y: int = x + 1
        print(y)
    x = 0  # error: x possibly assigned
    return x
\end{python}

\noindent Python assigns \pyinline{x} twice when \pyinline{b} is true, so no pure reading of the program agrees with
Python: under shadowing, \pyinline{return x} would refer to a different variable from the one assigned in the
branch.
\end{AddedBlock}
\noindent A variable \deleted{therefore }denotes
a fixed value once assigned, and features associated with mutation and shared state are excluded: \pyinline{global} and \pyinline{nonlocal}, which direct assignments to a variable of an enclosing scope;
\pyinline{del}, which removes a binding; augmented assignment (\pyinline{+=}, \pyinline{-=}, and so on); and
the walrus operator (\pyinline{:=}), which assigns within an expression. Assignment targets are variables, so item
assignment such as \pyinline{xs[0] = v} and attribute assignment such as \pyinline{p.x = v} are excluded, and methods
that update a value in place, such as \pyinline{list.append}, are unavailable, because only objects and modules have
attributes. A Python closure captures a binding rather than a value, so a change to the binding is visible through
the closure. Excluding reassignment removes such changes, a discipline Java imposes on captured locals, which must
be effectively final~\cite[\S15.27.2]{gosling2025}. One case remains: Python implements a comprehension by updating
its generator variables in place on each iteration, so \PurePy forbids a lambda in the body or in a later qualifier of a comprehension from
capturing a generator variable, since the updates would otherwise be visible through the lambda:

\begin{python}
[lambda x: x**i for i in [1, 2, 3]] # error: lambda captures i
\end{python}

\noindent Here each lambda computes \pyinline{x**3} in Python, since all three share the one binding of
\pyinline{i}.

\subsubsection{Scope}
\label{sec:scope}

Compatibility with mypy (\secref{python-compatibility}) settles the scoping of names in \PurePy. As in Python, a
scope is the body of a module, function, lambda or comprehension, and the builtins enclose every module. Python
does not distinguish definition from assignment, but mypy treats an annotation as a definition, and rejects a
declaration of a name already declared in the same scope, including as a parameter, imported name or pattern
variable. \PurePy follows mypy, so a function body, for example, cannot declare a name twice, whether on one path
or in different branches, nor redeclare one of its parameters. Like mypy, \PurePy permits shadowing: a scope may
declare a name of an enclosing scope, and the declaration then hides the enclosing variable throughout the scope,
so a use before the declaration is rejected as unbound\replaced{, where Python fails at run time with
\pyinline{UnboundLocalError}:}{. }
\begin{AddedBlock}
\begin{python}
y: int = 7
def f() -> int:
    x: int = y  # error: y is local
    y: int = 8
    return x
\end{python}
\end{AddedBlock}
\noindent The one exception in mypy is a use at module level of a
builtin name before its declaration, which refers to the builtin, as when Python runs the module. \PurePy treats
the builtins as an enclosing scope like any other, and rejects the use\replaced{.}{: }
\begin{DeletedBlock}
\begin{python}
n: int = len([1])  # error: len is bound by the module
len: int = 2
\end{python}
\end{DeletedBlock}
\noindent A pattern introduces its variables rather than assigning them, so a pattern cannot bind a name declared
in its scope either, although several cases of one match may bind the same variable.

\subsubsection{Control flow and effects}
\label{sec:no-effects}

\PurePy excludes loops with \pyinline{break} and \pyinline{continue}, exceptions
(\pyinline{try}/\allowbreak\pyinline{except}/\allowbreak\pyinline{raise}), context managers (\pyinline{with}), generators
(\pyinline{yield}/\allowbreak\pyinline{yield from}), and coroutines (\pyinline{async}/\allowbreak\pyinline{await}). Functional
programming has rich accounts of effects, from monads to algebraic effect handlers, so these features are not
inherently at odds with a functional language. In idiomatic Python, though, they are used mainly in
conjunction with mutable state, which \PurePy already excludes, and iteration is expressed by comprehensions
and recursion rather than by loops. A future release may add structured effects; for now the core stays
effect-free.

\subsubsection{Load-dependent meaning}
\label{sec:no-load-dependent}

A name's meaning in \PurePy must not depend on the order in which modules load or on runtime state, so several
of Python's import and module behaviours are excluded. Imports must appear at the start of a module, never
inside a function body or branch, nor after a statement, so that the dependencies of a module are known before
any of its statements runs. A submodule may not import itself through its parent
(\pyinline{from a import b} inside module \pyinline{a.b}): \PurePy treats the from-imported submodule as a
dependency, so this is an import cycle. An \pyinline{import} (as opposed to a from-import) may not name a
module contained in the importing module (\pyinline{import x.y} inside module \pyinline{x}), since the binding for
the head would denote the still-loading module.

A qualified reference must resolve through the imports of the referring module to a definitely assigned
member. A submodule is not an attribute of its parent until it is loaded, so
\pyinline{import pkg} followed by \pyinline{pkg.sub.y} is rejected unless the module also imports
\pyinline{pkg.sub}, whereas Python permits the reference whenever some earlier import, anywhere in the
program, happens to have loaded \pyinline{pkg.sub}:

\begin{minipage}[t]{0.25\textwidth}
\begin{python}
# a
import pkg.sub
\end{python}
\end{minipage}
\hfill
\begin{minipage}[t]{0.72\textwidth}
\begin{python}
# __main__
import pkg
import a
print(pkg.sub.y)  # error: pkg.sub is not imported here
\end{python}
\end{minipage}

\noindent Python accepts this because importing \pyinline{a} loads \pyinline{pkg.sub}; remove that import,
which the main module does not otherwise use, and Python raises \pyinline{AttributeError}. It raises the
same for a reference to a module member never assigned by the body, such as \pyinline{lib.x} where
\pyinline{lib} assigns \pyinline{x} only on a branch that is not taken. \PurePy rejects all three programs
statically (\secref{well-formedness-modules}).

A module may not bind a name that is also the name of one of its submodules. In Python an attribute of a
module can be set both by an assignment in the module body and by loading a same-named submodule, each
overwriting the other, so the value of the attribute depends on load order. \specref{sec:no-load-dependent} lists these exclusions, with an example.

\subsubsection{Modules and classes are not first-class}
\label{sec:no-first-class}

For now, modules and classes are not values in \PurePy. In Python a module is a value and a class definition
is an assignment, so both flow through programs as data. Treating them as first-class would complicate the
static account, so the present subset keeps them second-class rather than ruling the feature out; a later
release may revisit it. A module name may be projected by member access but not used as a value, and a class
name appears only at constructor and pattern positions, with class definitions confined to module level. Because a
class is identified by its fully-qualified name, a dataclass definition may not re-declare a name that already
denotes a class in the module; Python permits the re-declaration, leaving the earlier class reachable only
through its existing instances.

\subsubsection{Other restrictions}
\label{sec:other-restrictions}

A few remaining restrictions do not fit the groups above. Wildcard imports (\pyinline{from q import *})
are excluded, since the names introduced are not explicit; PEP 8 recommends against
them.\footnote{\url{https://peps.python.org/pep-0008/}} Every function definition annotates each
parameter and its return type, and every dataclass field carries a type expression, so the type of a
definition is given rather than inferred (\secref{well-formedness}); Python requires neither. A
\pyinline{class} definition must be a dataclass, and a dataclass body declares fields and nothing else. \PurePy therefore supports none of Python's
class-based extension mechanisms, such as \pyinline{__getitem__} for subscripting, \pyinline{__iter__} for
iteration or \pyinline{__eq__} for equality. Subscripting, iteration, equality and membership have the fixed
meanings given in \secref{operational-semantics}.

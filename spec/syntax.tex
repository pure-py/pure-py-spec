\section{Syntax}
\label{sec:syntax}

The syntax of \PurePy is given in \figrefThree{syntax-stmt}{syntax-expr}{syntax-types}. Statements are sequenced by
juxtaposition, $s\;s'$; a function body, a branch of a conditional and the body of a case are statements.
A \emph{top-level statement} $t$ is a statement or a class declaration, sequenced likewise; the body of a
module after its imports is a top-level statement, so class declarations occur only at the top level of a
module. A \emph{mutual region} $d_1 \ldots d_{n+1}$ is a maximal
run of consecutive \pyinline{def} statements in a sequence: any other statement separates mutual
regions. Maximality is not enforced by the grammar in \figref{syntax-stmt}; the parser is responsible for
grouping consecutive \pyinline{def}s into a single mutual region. The well-formedness rules treat each
mutual region as one mutually-recursive binding\paperonly{ (see \secref{mutual-recursion})}.
\figref{metavariables} summarises the metavariables used throughout.

\subsection{Lexical syntax}
\label{sec:lexical}

The grammar of \PurePy is an abstract syntax, and its metavariables range over values rather than
over source text: $n$ is a number and $w$ is a string, not the lexemes that denote them. A number is never
negative, since Python writes a negative number as unary minus applied to a literal, and a length or an
exit status is an integer. How source text
becomes abstract syntax follows Python, including the indentation that delimits blocks.

\subsection{Contexts}
\label{sec:contexts}

Metavariables $x$, $f$, $c$ range over \emph{variables}, simple identifiers whatever they denote; idiomatically $f$ is used when the variable is expected to denote a function and $c$ when it is expected to denote a class. A \emph{qualified name} $q$ is a non-empty sequence of variables separated by dots (\figref{syntax-stmt}); a variable is thus a qualified name with a single component.

\begin{definition}[Context]
\label{def:context}
A context $\Gamma$ (or $\Delta$) is a finite map from variables to one of the following \emph{context entries} $\theta$:
\begin{itemize}
\item the variable's \emph{definite assignment} status $b \in \B = \set{\statusDefAssigned, \statusNotDefAssigned}$;
\item a \emph{module reference}, for a fully-qualified module name $q$: either a \emph{stub} $\modStub{q}$, or \emph{loaded} reference $\modLoaded{q}{\Gamma}$ carrying the \emph{signature} $\Gamma$ of $q$, the context specifying its members;
\item a \emph{class entry} $C$, of the form $\clsEntry{\Gamma}{q.c}{\bind{\seq{x}}{\seq{\tau}}}{c'}$, recording the declaring context $\Gamma$, the qualified name $q.c$ of the class, sequence of distinct fields $\seq{x}$ with their declared types $\seq{\tau}$, and base class name $c'$ (or $\bot$ for no base).
\end{itemize}
\end{definition}

\noindent Module references arise from import statements. A module declares each class name at most once, so the qualified name of a class entry is the identity of the class. The definite-assignment terminology is borrowed from Java~\cite[\S16]{gosling2025}; $\statusDefAssigned$ indicates \emph{definitely assigned} and $\statusNotDefAssigned$ \emph{not definitely assigned} (or, equivalently, degenerate types ``any'' and ``none'').
It is useful to represent contexts as total functions on the set of all variables by extending the codomain with $\bot$ to indicate \emph{undefined}. We write $\Gamma, \bind{x}{\theta}$ for the context that sends $x$ to $\theta$ and otherwise agrees with $\Gamma$, define $\dom(\Gamma) = \set{x \mid \Gamma(x) \neq \bot}$, and write $\varnothing$ for the context where all variables are undefined. For a set of variables $X$, write $\statusDefAssigned(X)$ for the context $\set{\bind{x}{\statusDefAssigned} \mid x \in X}$; similarly $\statusNotDefAssigned(X)$.

An \emph{argument list} $a$ (\figref{syntax-expr}) is a sequence of positional arguments followed by
keyword arguments $x = u$, where an argument $u$ is an expression in a constructor call and a pattern in a
constructor pattern. $\fieldMap$ (\secref{auxiliary-classes}) pairs the arguments of $a$ with the fields
they supply.

\paragraph{Context operations.}

Contexts admit a non-commutative monoid of sequential composition $\Gamma \override \Delta$ (``override'') and
an idempotent commutative semigroup of parallel composition $\merge$ (``merge''). Together these form a
\emph{right near-semiring}~\cite{vanhoorn1967}: $\override$ right-distributes over $\merge$, but left
distributivity does not hold. Both are defined pointwise (\figref{context-ops}): override is right-biased
and has $\bot$ as both left and right unit; merge is defined only on definite-assignment statuses, returning
$\statusNotDefAssigned$ when exactly one argument is defined and the conjunction otherwise, so $\bot$ is not
a unit.
\input{spec/fig/context-ops}

A third operation, \emph{context extension} $\Gamma \extend \Delta$, also \figref{context-ops},
combines module references for the same module recursively, preferring loaded references to stubs, and is
otherwise right-biased like override. It is used when processing import prefixes, where two imports rooted
at the same module must combine rather than shadow.

\paragraph{Operators.}

The metavariable $\odot$ ranges over the supported binary operators other than \pyinline{and} and
\pyinline{or}, and $\ominus$ over the supported unary
operators, both enumerated in \figref{precedence}. The operators \pyinline{and} and \pyinline{or} have their own
expression forms; they do not evaluate both operands. The grammar of \figref{syntax-expr} is intentionally ambiguous
on operator forms; disambiguation is by the precedence and associativity given in \figref{precedence},
which follow Python.

\input{spec/fig/precedence}

\paragraph{Type annotations.}

Parameters and assignments carry optional type annotations $\pi$ and function definitions optional return
type annotations $\omega$, while dataclass fields carry types $\tau$; types and annotations are given in
\figref{syntax-types}. We write $\seq{x}\,\seq{\pi}$ for the parameter list $x_1\pi_1, \ldots,
x_n\pi_n$. The well-formedness rules and operational semantics do not consult annotations, which are given
meaning by the type system.

\subsection{Modules and programs}
\label{sec:modules-programs}

A \PurePy \emph{program} is a finite map $\mathcal{M}$ from \emph{fully-qualified module names}
(\figref{syntax-stmt}) to \emph{module bodies} $\mu$, of which one is a distinguished \emph{main module} named
$\pymath{\_\_main\_\_}$; here $\nameOf(q)$ is the string literal naming $q$, so
$\nameOf(\pymath{\_\_main\_\_}) = \pymath{"\_\_main\_\_"}$. We identify a module with its fully-qualified name, writing ``module $q$'' for the module named $q$. A module body is a sequence of imports
$\seq{\iota}$, its \emph{import prefix}, followed by a top-level statement $t$; since imports are not statements, they can appear neither
within a statement nor after it. The statement begins with the
assignment $\exAssign{\pymath{\_\_name\_\_}}{\nameOf(q)}$, which binds the module's name when it
loads (\secref{well-formedness-modules}).

A second map $\mathcal{P}$ gives the
predefined modules of \figref{predefined}, which have no body: $\mathcal{P}$ takes each such name to its
environment and context (Definition~\ref{def:predefined}). The two domains are disjoint, and their union is
prefix-closed: the parent of any module in $\dom(\mathcal{M}) \cup \dom(\mathcal{P})$ is itself in
$\dom(\mathcal{M}) \cup \dom(\mathcal{P})$.\footnote{A source tree encodes such an $\mathcal{M}$: its modules are the \texttt{.py} files and the
directories, each named by its path, so the domain is prefix-closed by construction. A module's statement is
the statements of its \texttt{.py} file, or of its \texttt{\_\_init\_\_.py} for a directory, preceded by the
$\pymath{\_\_name\_\_}$ assignment; a directory without an \texttt{\_\_init\_\_.py} (a namespace package,
PEP 420, \url{https://peps.python.org/pep-0420/}) contributes that assignment alone.} The maps $\mathcal{M}$ and $\mathcal{P}$ are fixed and ambient in all
definitions that follow, as is the name $q$ of the enclosing module in the rules that check or evaluate a single module's body.


\begin{definition}[Predefined contexts and environments]
\label{def:predefined}
$\mathcal{P}$ takes each module $q$ of \figref{predefined} to a pair $(\rho, \Gamma)$, where $\rho$ binds
$\pymath{\_\_name\_\_}$ to $\nameOf(q)$ and each member listed for $q$ in \figref{predefined} to its value
(\figref{predefined-values}),
and $\Gamma$ binds $\pymath{\_\_name\_\_}$ at $\tyStr$ and each member at the type listed for it, or at
$\statusDefAssigned$ where the figure lists none.
\end{definition}

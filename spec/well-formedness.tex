\section{Well-formedness}
\label{sec:well-formedness}

\PurePy excludes some Python behaviours statically and others only at runtime.
Well-formedness is the static part, a judgement on programs defined in this \seckind{}; the operational
semantics (\secref{operational-semantics}) is defined for well-formed programs. The statement and expression rules rest on a definite-assignment analysis; the pattern rules
enforce linearity and reachability; and the module rules govern imports and class declarations. The
\seckind{} follows the syntax of \secref{syntax}, taking statements, expressions and patterns, then modules
and programs, and \secref{operational-semantics} gives each of these a dynamic counterpart.

\subsection{Types}
\label{sec:types}

The typing rules say whether a program is well typed. They are intended as a refinement of mypy's: a well-typed
\PurePy program should be accepted by mypy, and \PurePy may reject programs mypy accepts but not the
reverse. Function signatures, assignments and dataclass fields are annotated with type expressions, and a
type expression denotes a type under a context (\figref{resolve-type}). Every definition carries an
annotation for each parameter and for its return type, so the type of a definition is given rather than
inferred from its body. A class name resolves to a
class (\figref{resolve-name}) and every other name must resolve to a predefined entry
(\figref{predefined-types}). The \emph{base type} $\baseType(\tau)$ discards the precision of a
literal type, taking $\tyLiteral{42}$ to \pyinline{int} and leaving every other type alone
(\secref{types-auxiliary}).

The context entry for a definitely assigned variable is its type (Definition~\ref{def:context}), and a variable
that is not definitely assigned is bound to $\statusNotDefAssigned$. Two contexts from different branches of a conditional merge pointwise. A variable definitely assigned in both, at $\sigma$ and $\tau$, is of type
$\joinTy(\sigma, \tau)$, whereas a variable definitely assigned in one branch alone is
$\statusNotDefAssigned$.

\subsection{Subtyping}
\label{sec:subtyping}

Subtyping (\figref{subtyping}) has every type below itself, a literal type below its base type, and a class below its
ancestors, with \pyinline{object} above every type and \pyinline{Never} below every type. A union is above
each of its members and below every type that is above all of them. A tuple type is covariant, below another of the
same length whose components are above its own. Two types are \emph{equivalent}, $\sigma \tyEquiv \tau$, when each is a subtype of the other; both notations follow \citet{pierce2002}. Lists,
dictionaries and callables are related only where their components are equivalent, since \pyinline{list}
and \pyinline{dict} are invariant in mypy and covariance would accept programs mypy rejects. The types with a length, namely lists, dictionaries,
strings and tuples, are below \pyinline{Sized}. An \pyinline{int} is a \pyinline{float}, as PEP~484
requires, so \pyinline{x: float = 0} is well typed. A \pyinline{bool} is not an \pyinline{int}, although
Python treats it as one.

\begin{lemma}[Transitivity of subtyping]
\label{lem:subtyping-transitive}
If $\sigma \subty \tau$ and $\tau \subty \tau'$ then $\sigma \subty \tau'$.
\end{lemma}

Two types are \emph{comparable}
when either is a subtype of the other. Two comparable types
\emph{join} to the larger type and two incomparable types to their union. A sequence of types joins by
joining the first with the join of the rest, with \pyinline{Never} as the unit (\secref{types-auxiliary}).
So joining a type with itself gives that type, joining a class with one of its ancestors gives the ancestor, and
joining \pyinline{int} with \pyinline{str} gives $\tyUnion{\tyInt}{\tyStr}$.

\subsection{Statements}
\label{sec:well-formedness-statements}

Every well-typed statement either \emph{definitely returns}, or \emph{definitely assigns} a context
$\Delta$, which may be empty. The base cases are that \pyinline{return e} definitely returns, and
\pyinline{x = e} definitely assigns $\set{\bind{\pyinline{x}}{\sigma}}$ for the type $\sigma$ of
\pyinline{e}. \emph{Result types} $R$ classify these outcomes: $R$ is either $\Returns$ (definitely
returns) or $\Assigns{\Delta}$ (definitely assigns $\Delta$).

Context operations $\override$ and $\merge$ lift to a right semiring over result types $R$, with $\Assigns{\varnothing}$ as left and right unit for $\override$ and $\Returns$ as unit for $\merge$ and zero for $\override$.

\begin{definition}[Override and merge on result types]
\begin{defalign}
\Assigns{\Delta} \merge \Assigns{\Delta'} & = \Assigns{(\Delta \merge \Delta')} \\
R \merge \Returns = \Returns \merge R & = R \\
\\
\Assigns{\Delta} \override \Assigns{\Delta'} & = \Assigns{(\Delta \override \Delta')} \\
R \override \Returns = \Returns \override R & = \Returns
\end{defalign}
\end{definition}

\noindent The $\Returns \override R$ case never arises because the statement judgement excludes unreachable statements\paperonly{ (\secref{unreachable})}.

A sequence $s\;s'$ (\ruleName{seq}) types $s$, types $s'$ under $\Gamma$ overridden by what $s$
assigns, and requires that no variable captured by $s$ is assigned in $s'$. A conditional combines its
branches with $\merge$, merging in $\Assigns{\varnothing}$ when there is no \pyinline{else} branch.

$\Gamma; \zeta \vdash s : R$ says that $s$ has result type $R$ in $\Gamma$, with return type $\zeta$
(\figref{typing-stmt}); every rule passes $\zeta$ down unchanged. Top-level statements have a judgement of
their own, $\Gamma \vdash t : R$ (\figref{typing-top}): a sequence composes as a statement sequence does, a
class declaration is a top-level form, and a plain statement is checked with no return type
(\ruleName{top-stmt}), so a \pyinline{return} has no derivation at the top level. A top-level
statement may not assign a name that an earlier top-level statement bound to a class
(\ruleName{top-seq}), so a class binding is permanent in its module and no later declaration or
assignment can take a declared class's name. A
\pyinline{return} checks its expression against $\zeta$, and a bare \pyinline{return} requires $\zeta$ to
admit \pyinline{None}. An annotated assignment checks the expression against the type of the annotation,
and an unannotated assignment takes the type the expression synthesises (\ruleName{assign},
\ruleName{assign-unannot}). The conditions of \pyinline{if} and \pyinline{assert}
check against \pyinline{bool}, and an assertion message against \pyinline{str}. A class declaration binds
the class name to $\Type{C}$, requiring the class's own fields to be distinct and, where it extends
another class, the base name to be bound to a class and the own fields not to repeat an inherited one
(\ruleName{class}, \ruleName{class-extend}). It also requires \pyinline{dataclass} to be in scope, since
the declaration names it. Each rule that takes an annotation resolves it to a type
(\figref{resolve-type}).

A function definition binds its parameters at their annotated types and its own name, and the names of the
mutual region it belongs to, each at its $\pyinline{Callable}$ type; variables assigned in the body start
at $\statusNotDefAssigned$ (\ruleName{def}). The body is checked with the
declared return type, and must have result type $\Returns$ unless the function returns \pyinline{None},
so a function that declares a result definitely returns one.

A \pyinline{match} scrutinee synthesises a type $\sigma$, and the cases are taken in turn from
$\shapesOf(\sigma, \varnothing)$, which denotes every value of $\sigma$. The \emph{residual} $L_i$ holds
the values which have not been matched by any case up to the $i$th. Each case matches its pattern against
the residual by the \ruleName{cases} rule (\figref{pat-rows}), yielding the pattern's bindings and the
shapes left unmatched; the body is checked under the bindings, and the pattern must agree with $\sigma$
(\figref{agrees}). The \ruleName{match} rule applies where the final residual is empty;
\ruleName{match-partial} applies otherwise, merging in $\Assigns{\varnothing}$ for the values that fall
through. A literal-typed scrutinee is exhausted by covering its literals, so \pyinline{x = 42} admits a
match with a case for \pyinline{42} alone; \pyinline{x: int = 42} keeps the type open.

Name resolution takes a qualified name to a context entry (\figref{resolve-name}).
A variable is a well-formed expression when it is definitely assigned (\ruleName{wf-var});
a lambda checks its body with its parameters definitely assigned, and a comprehension checks its body
with the variables bound by its generators definitely assigned (\ruleName{wf-qual-generator}). A lambda within
a comprehension may not capture a generator variable, a side condition of \ruleName{wf-list-comp},
\ruleName{wf-dict-comp} and \ruleName{wf-qual-generator}, because Python mutates the variable on each iteration
and the lambda would see its final value. A module attribute reference $\exAttr{e}{x}$ is well-formed
when, read as a qualified name, it resolves to a definitely assigned member
(\ruleName{wf-attr-module})\paperonly{; see \secref{no-load-dependent}}. A constructor call requires its name
to resolve to a class and its arguments to cover the class's fields exactly, through $\fieldMap$
(\ruleName{wf-constr}). A variable bound to a module or class is not an expression on its own, and occurs
only as the head of a qualified name\paperonly{ (\secref{no-first-class})}.

\input{spec/fig/well-formed-expr}

Pattern subsumption $\Gamma \vdash p \subsumed p'$\speconly{ (\figref{subsumption})}\paperonly{ (defined in \specification)} is a
preorder on patterns under which every value matched by $p$ is also matched by $p'$. A pattern list is
well-formed (\figref{well-formed-pat}) when each pattern is linear (no pattern variable occurs more than
once), each constructor pattern names a class and its sub-patterns cover the class's fields exactly
(\ruleName{wf-pat-constr}), and no earlier pattern subsumes a later one (\ruleName{wf-cases-cons}), so that
every case of a \pyinline{match} is reachable. Exhaustiveness is a separate test; without a type system
to bound the values a match may receive, it degenerates to whether the last case is a catch-all.

\subsection{Modules and programs}
\label{sec:well-formedness-modules}

\emph{Static loading} checks a module's body and computes its signature $\Gamma$, the judgement
$\vdash_{\mathsf{load}} q : \Gamma$ (\figref{well-formed-module}); it mirrors loading at run time (\secref{operational-semantics}).
Both import forms statically load their target, together with its ancestors
(\figref{well-formed-imports}). A plain import also records each of these modules as a member of its
parent (the static loads-as judgement), so that the binding created for the root of the target gives attribute
access along the whole chain. A from-import also loads any imported name that denotes a submodule. An
ancestor of the target is exempt from loading first if it is the importing module or one of its
ancestors, since at runtime it may still be loading. The exemption applies only to from-imports, because
for a plain import
the only ancestor that could never load first is the importing module itself, and an import naming a proper
descendant of the importing module is excluded outright\paperonly{ (\secref{no-load-dependent})}. Loading a module
may thus require other modules to load first; the rules are interpreted inductively, so a program with an
import cycle is ill-formed, because a module in a cycle could finish loading only after itself. Program
well-formedness (\figref{well-formed-module}) requires the main module to be well-formed and hence,
recursively, every module the program can load; a module that is never imported is not checked.
The rule \ruleName{wf-module} checks a module body under the context of $\mathcal{P}(\pyinline{builtins})$,
overridden by the imported context, so the members of \pyinline{builtins} are in scope
unqualified.

\input{spec/fig/well-formed-module}

The signature $\Gamma$ that static loading produces (\figref{well-formed-module}) comprises the classes
and variables a module defines, together with its intrinsic \pyinline{__name__} and a stub for each submodule,
never the names it imports: following PEP 484\footnote{\url{https://peps.python.org/pep-0484/}}, an imported
name is a private dependency, not re-exported as part of the interface. Submodule stubs and the module's own
bindings are disjoint, because the module rules exclude a module that binds a name that is also the name of
a submodule\paperonly{ (\secref{no-load-dependent})}.

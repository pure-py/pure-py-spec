\section{Well-formedness}
\label{sec:well-formedness}

\PurePy excludes some Python behaviours statically and others only at runtime.
Well-formedness is the static part, a judgement on programs defined in this \seckind{}; the operational
semantics (\secref{operational-semantics}) is defined for well-formed programs. A program is well-formed
when it is well typed, so the rules of this \seckind{} give each expression a type, each statement a
static outcome recording either the assignments made or the fact that the statement definitely returns,
and each module a signature. The \seckind{} introduces
types and subtyping, then follows the syntax of \secref{syntax}, taking statements, expressions and
patterns, then modules and programs, and \secref{operational-semantics} gives each of these a dynamic
counterpart.

The rules for variables serve two aims: that a program has no mutable state, so a variable never
changes value, and that a well-typed program is also well typed under mypy, unless mypy rejects the program because of a behaviour reported as a bug (\secref{mypy-restrictions}). Within these limits the rules permit
as much as possible. For the first aim, a variable is introduced by a declaration, parameter, import, pattern or
generator, and is assigned at most once, either in its declaration or afterwards; an assignment never introduces
a variable nor reassigns one.
For the second, a scope is the body of a module, function, lambda or comprehension, as in Python, and the
builtins enclose every module; a scope declares a name at most once and may shadow a name of an enclosing scope,
hiding it throughout the scope.

\subsection{Types}
\label{sec:types}

\input{spec/fig/resolve-name}
\input{spec/fig/resolve-type}

Function signatures, assignments and dataclass fields are annotated with type expressions, and a
type expression denotes a type under a context and class table (\specfigref{resolve-type}). Every definition carries an
annotation for its parameters and return type, so the type of a definition is given rather than
inferred from its body. Within a type expression, a class name applied to as many type arguments as the class has parameters resolves to an instantiated class, an alias name applied to type arguments resolves to the instantiation of its alias, type parameters in scope denote the type variables of those names, and all other names must be predefined names (\specfigref{resolve-type}). The function $\baseType(\tau)$ discards the precision of a
literal type, taking $\tyLiteral{42}$ to \pyinline{int} and otherwise acting as the identity
(\S\ref{aux:base-type}).

\subsubsection{Subtyping}\label{sec:subtyping}%

Subtyping (\specfigref{subtyping}) has every type below itself, a literal type below its base type, and an instantiated class $C[\seq{\tau}]$ below every type that its base class is below, once $\seq{\tau}$ is substituted into the arguments of the base (\ruleName{subty-class-extend}), and below $C[\seq{\sigma}]$ when $\seq{\tau}$ and $\seq{\sigma}$ are equivalent (\ruleName{subty-class}), so that type arguments are invariant, as for lists and dictionaries; a type variable is below itself and \pyinline{object} alone, with \pyinline{object} above every type and \pyinline{Never} below every type. A type that is not a union has one \emph{disjunct}, the type itself; the disjuncts of a union $\tyUnion{\sigma}{\tau}$ are the disjuncts of $\sigma$ together with the disjuncts of $\tau$. A union is above
each of its disjuncts and below every type that is above all of them. A tuple type is covariant, below another of the
same length when each of its components is below the corresponding component. Two types are \emph{equivalent}, $\sigma \tyEquiv \tau$, when each is a subtype of the other; the notations $\subty$ and $\tyEquiv$ follow \citet{pierce2002}. Lists and
dictionaries are related only when their components are equivalent, since both are invariant in mypy (\secref{mypy-restrictions}). A callable type is contravariant in its parameters
and covariant in its result, following mypy. The types with a length, namely lists, dictionaries,
strings, tuples and $\clsRange[]$, are below \pyinline{Sized}. An \pyinline{int} is a \pyinline{float}, as PEP~484
requires, so \pyinline{x: float = 0} is well typed. A \pyinline{bool} is not an \pyinline{int}, although
Python treats it as one.

\noindent Subtyping is therefore a preorder: reflexive and transitive but not antisymmetric,
because distinct types such as $\tyUnion{\sigma}{\tau}$ and $\tyUnion{\tau}{\sigma}$ are
equivalent.

\subsection{Expressions}
\label{sec:expression-typing}

Within an expression the typing judgement gives each subexpression a type, and
is bidirectional. \emph{Synthesis} $\Sigma; \Gamma \vdash e \synth \tau$ reads a type out of an expression (\specfigrefThree{typing-synth}{typing-synth-elim}{typing-synth-ctd}),
and \emph{checking} $\Sigma; \Gamma \vdash e \checks \tau$ tests an expression against a type supplied by its
surroundings (\specfigref{typing-check}). The division follows the usual recipe for bidirectional
systems~\cite{davies2000,dunfield2021}: introduction forms check, since a lambda's parameters cannot be
annotated and an empty list does not determine its element type, and elimination forms synthesise, since a call, a subscript or an attribute
reference starts from a subterm whose type is known. Python has no annotation form
$(e \mathbin{:} \tau)$, by which such systems usually let a checking form occur where synthesis is required, so
\PurePy gives each introduction form a synthesis rule wherever its parts determine the type, an approach also taken
by Swift, Kotlin and Scala~\cite{swift2025,kotlin2025,odersky2025}.

Variables, literals, attribute references, calls, constructor calls, operators and subscripts synthesise.
A variable synthesises a type only when its context entry is a type (\ruleName{var}), so a variable that is not definitely
assigned, or a name bound at a type scheme, does not synthesise a type. A
literal $\ell$ synthesises the literal type $\tyLiteral{\ell}$, except for a float literal, which synthesises \pyinline{float}.

\input{spec/fig/typing-synth}

The fields of a class $C$ form a field scheme $\fields{\Sigma}(C)$ over its type parameters, with one binding $\bind{x}{\tau}$ per
field: the fields of its base class first, recursively and instantiated at the type arguments of the base, then the fields declared by $C$ itself, each at its
declared type; the fields of an instantiated class $C[\seq{\tau}]$ are the instantiation $\tyInst{\fields{\Sigma}(C)}{\seq{\tau}}$. The order matters, because a constructor call pairs positional arguments with fields by
position. A call $\exCall{q}{a}$ is a constructor call if $q$ denotes a class. A constructor call pairs each argument with a field using $\fieldMap{\Sigma}$ and
infers type arguments $\seq{\tau}'$ for the class $C$ that $q$ resolves to, using $\typeArgs{\Sigma}$
(\S\ref{aux:type-args}) over the arguments that synthesise, as
in \ruleName{callee-scheme} (\ruleName{constr}). The arguments are checked against the field types instantiated at
$\seq{\tau}'$, and the call synthesises $C[\seq{\tau}']$. A constructor call of the form $\exCall{q[\seq{\psi}]}{a}$ takes
the type arguments denoted by $\seq{\psi}$ instead (\ruleName{constr-explicit}). An attribute reference $\exAttr{e}{x}$ has the type of the field $x$ of the class synthesised by $e$
(\ruleName{attr-object}). The signature of a predefined module binds
$\pymath{\_\_name\_\_}$ at $\tyStr$ and each member at the type given in \figref{predefined-signatures}
(Definition~\ref{def:predefined}). A module attribute reference
$\exAttr{e}{x}$ resolves as a qualified name to a definitely assigned member
(\ruleName{attr-module}). A variable bound to a module or
class is not an expression on its own, and occurs only as the head of a qualified
name.
In a subscript $\exSubscript{e}{e'}$ there is a rule for each container that $e$ can synthesise: a list
(\ruleName{subscript-list}) or string (\ruleName{subscript-str}) with $e'$ of type \pyinline{int}, and a
dictionary with $e'$ of type \pyinline{str} (\ruleName{subscript-dict}). Tuples have three rules: an index of type \pyinline{int} gives
the join of the component types (\ruleName{subscript-tuple-int}), unless it synthesises a literal type, in which case it
gives the component type at that position, counting from the end when the index is negative
(\ruleName{subscript-tuple}, \ruleName{subscript-tuple-neg}).
A subscript, attribute reference or call with a subject synthesising a union is typed at each disjunct, with a variable in place of the subject, and synthesises the
join of the results (\ruleName{subscript-union}, \ruleName{attr-union}, \ruleName{call-union}).
Generators need no such rule, because $\elemTy{\Sigma}$ takes a union to the join of its disjuncts' element types.
\citet{dunfield2004} state union elimination once, for an arbitrary evaluation context; here union elimination is
stated separately for each elimination form.

The \ruleName{call} rule for a call $\exCall{e}{\seq{e}}$ uses the auxiliary
judgement $\Sigma; \Gamma \vdash e, \seq{e} \synth \seq{\sigma}, \sigma$ (\specfigref{typing-callee}), which determines parameter
types $\seq{\sigma}$ and return type $\sigma$ from the callee along with its arguments. The remaining premises check
the arguments against $\seq{\sigma}$, and the call synthesises $\sigma$. The auxiliary judgement has two rules. A callee that synthesises a
\pyinline{Callable} type gives the parameter and return types of that type (\ruleName{callee}). A name bound at a
type scheme $\scheme{\seq{\alpha}}{\tyCallable{\seq{\sigma}}{\sigma}}$ instantiates the type parameters from the arguments
(\ruleName{callee-scheme}). The type arguments are collected by $\typeArgs{\Sigma}$
(\S\ref{aux:type-args}) over the arguments that synthesise,
by a one-way unification of each parameter type with the synthesised type, in which the type parameters $\seq{\alpha}$ are the
unknowns: a type parameter takes the type found at the same
position in the synthesised type, with one found at several positions taking the join of those types.
Arguments that do not synthesise, such as lambdas, are left out. The parameter and return types are
instantiated at the type arguments given by the context, which must bind every type parameter.

Lambdas, applied lambdas, lists, tuples, dictionaries, conditional expressions and comprehensions check
(\ruleName{lambda}, \ruleName{call-lambda}, \ruleName{list}, \ruleName{tuple}, \ruleName{dict}, \ruleName{cond},
\ruleName{list-comp}, \ruleName{dict-comp}).
A name bound at a type scheme $\scheme{\seq{\alpha}}{\sigma}$ checks against a type $\tau$
by instantiating $\seq{\alpha}$ at the type arguments collected by $\typeArgs{\Sigma}$ from $\sigma$ and $\tau$, provided the
instantiated $\sigma$ is below $\tau$ (\ruleName{var-scheme}), so a function with type parameters can be passed where a \pyinline{Callable} type is expected.
An expression that synthesises $\sigma$ checks against any supertype
of $\sigma$ (\ruleName{check-syn}), which applies only when no other rule concludes $\Sigma; \Gamma \vdash e \checks
\tau$, so both judgements are
syntax-directed and an expression has at most one derivation in each. The \ruleName{simple-scheme} resolution rule
(\figref{resolve-name}) requires the type parameters to be non-empty, so \ruleName{callee-scheme} and \ruleName{var-scheme}
do not apply to names bound at \pyinline{Callable} types, although they would conclude the same as \ruleName{callee} and
\ruleName{check-syn}.

\input{spec/fig/typing-check}

The forms that synthesise are conditional expressions when a branch
synthesises, at the join of the two types when both branches synthesise and otherwise at the
synthesising branch's type, the other branch checking against it (\ruleName{cond-syn});
tuples when every component synthesises (\ruleName{syn-tuple}); comprehensions when the body
synthesises (\ruleName{syn-list-comp}, \ruleName{syn-dict-comp}); and non-empty lists and
dictionaries when at least one element synthesises, the remaining elements checking against the join
of the base types of the synthesising elements (\ruleName{syn-list}, \ruleName{syn-dict}). A list,
dictionary or comprehension takes the base type of the type synthesised by its elements or body, since
\pyinline{list} and \pyinline{dict} are invariant and a literal element type would keep the container from
matching any other element type. An empty list or dictionary and a lambda have no
synthesis rule at all, so checking is the only way to type them. A lambda applied to arguments is the
exception, since the arguments give the parameter types, and the call then synthesises the type of the body
or checks the body against an expected type (\ruleName{call-lambda-syn}, \ruleName{call-lambda}). The parameters of a
lambda must be distinct, as for a function. A non-empty list has both, and the
checking rule is still needed when the expected element type is wider than the type synthesised by the
elements, since \pyinline{list} is invariant.

Typing a comprehension types its qualifiers, which bind the variables that can be used in the body
(\figref{typing-check}). A generator's variable is bound at $\elemTy{\Sigma}$ of the type synthesised by the
iterated expression (\S\ref{aux:elem-type}). A
tuple is iterated at the join of the base types of its components.
A lambda within a comprehension may not capture a generator variable, a side condition of
\ruleName{list-comp}, \ruleName{dict-comp} and \ruleName{qual-generator}. Python closures are
late-binding and the comprehension rebinds the variable on each iteration, so the lambda would see the
variable's final value; in \PurePy a lambda is only able to see the value of the generator variable at
each iteration.

\subsubsection{Operators}\label{sec:well-formedness-operators}%

\input{spec/fig/operator-overloads}

Each operator is overloaded as specified in \specfigref{operator-overloads}. The operator \pyinline{|} has no overloads, so an expression $\exBinOp{e}{\pyinline{|}}{e'}$ does not synthesise a type; the operator occurs only within type expressions, where $\tyUnion{\psi}{\psi'}$ denotes a union (\ruleName{ty-union}).

\begin{specdefinition}{Resolved overload}
A \emph{resolved overload}
$((\tau_1, \tau_2), \tau)$ pairs operand \emph{bounds}
with a return type; the judgements of the figure relate operand
types to the resolved overloads of an operator.
\end{specdefinition}

The \ruleName{binop} and \ruleName{unop} rules (\specfigref{typing-synth}) take the return type
of the most specific overload at the operand types, $\resolveOp{\Sigma}$ (\S\ref{aux:resolve-op}), so \pyinline{1 + 2} is an
\pyinline{int} and \pyinline{1 + 2.0} a \pyinline{float}. \added{Operators also have rules for elimination at a union (\figref{typing-synth-elim}), which
apply when no overload applies at an operand of union type: the operator is typed at each disjunct, left operand
first, and synthesises the join of the results (\ruleName{binop-union-left}, \ruleName{binop-union-right},
\ruleName{unop-union}). With \pyinline{x} of type
$\tyUnion{\tyInt}{\tyStr}$, the expression \pyinline{x * 2} synthesises $\tyUnion{\tyInt}{\tyStr}$. The order follows the argument type expansion
step of the Python typing specification's algorithm for calls to overloaded functions~\cite{typingcouncil2025}.}

\input{spec/fig/needs-eq}

The judgement $\Sigma \vdash \tau \needsEq \xi$ (\figref{needs-eq-type}) states that equality at $\tau$ needs equality at type variable $\xi$, or at a callable type when $\xi$ is $\varepsilon$. The judgement $\Sigma \vdash C \needsEq \xi$ (\figref{needs-eq-class}) states the same of class $C$, where $\xi$ is a type parameter of $C$ or $\varepsilon$, by the field types of $C$. The overloads of \pyinline{==} and \pyinline{!=} (\figref{operator-overloads}) require operand types $\tau$ with $\Sigma \nvdash \tau \needsEq \xi$ for every $\xi$, the \emph{equality types}: comparing two values of type $\tau$ never reaches a type variable, whose instantiation is unknown, or a callable type, whose values cannot be compared. For example, a class $C$ with type parameter $\alpha$ and a single field of type $\tyUnion{C[\alpha]}{\tyNone}$, which mentions $C$ through a type alias, does not need equality at $\alpha$ or at a callable type, so $C[\sigma]$ is an equality type for every $\sigma$. Comparisons of functions are therefore rejected statically, and values of an equality type are compared by structural equality, which is defined except at the dynamically excluded comparisons (\secref{no-coercions}).

The final rule of each table closes the
judgement under base-typing, letting \pyinline{1 == 0} use the equality overload at \pyinline{int}, since
two distinct literal types are not comparable; \pyinline{2 ** 3} is still an \pyinline{int}, since the
direct instance's bounds $(\tyInt, \tyLiteral{3})$ lie below the base instance's
$(\tyFloat, \tyFloat)$. For this operator the \ruleName{binop} rule is more precise than mypy, whose
overloads give \pyinline{Any} whenever the exponent is not a literal, whereas the most specific overload resolves to
\pyinline{float}.

\begin{lemma}[Most specific overload]
\label{lem:most-specific-overload}
If neither $\sigma_1$ nor $\sigma_2$ is a subtype of \pyinline{Never} and some overload of $\odot$ applies at
$(\sigma_1, \sigma_2)$, then $\resolveOp{\Sigma}(\odot, \sigma_1, \sigma_2)$ is defined, and similarly for
$\resolveOp{\Sigma}(\ominus, \sigma)$.
\end{lemma}

\label{sec:well-formedness-statements}

\input{spec/fig/typing-stmt}

The statement judgement $\Sigma; \Gamma; \zeta \vdash s : R$ says that under $\Gamma$ and
optional return type $\zeta$, statement $s$ has static outcome $R$ (\specfigref{typing-stmt}); every rule passes $\zeta$ down unchanged.
A sequence $\exSeq{s}{s'}$ (\ruleName{seq}) types $s$, then types $s'$ under $\Gamma$ overridden by the context assigned
by $s$. A conditional combines its
branches with $\merge_{\Sigma}$, merging in $\Assigns{\varnothing}$ when there is no \pyinline{else} branch (\ruleName{if}, \ruleName{if-else}).
A
\pyinline{return} checks its expression against $\zeta$, which must be of the form $\tau$, and a bare
\pyinline{return} requires $\tau$ to be equivalent to \pyinline{None} (\ruleName{return}, \ruleName{return-none}). An expression statement is typed by one of two rules. If its expression synthesises a type, the
type is discarded (\ruleName{expr-stmt}). A call to a callable with result \tyNone{} does not synthesise a
type, following mypy (\secref{mypy-restrictions}), which
rejects such a call wherever a value is required; such calls are typed instead by \ruleName{call-stmt}, which
just checks the arguments against the parameter types. Both rules give the static outcome
$\Assigns{\varnothing}$. A call statement with a callee synthesising a union is typed
once per disjunct (\ruleName{call-stmt-union}), following \ruleName{call-union} for a call expression.

A variable declaration $x\exAnnot{\psi}$ introduces $x$ at the type denoted by $\psi$, without assigning it
(\ruleName{declare}); an assignment $\exAssign{x}{e}$ requires $x$ to be a declared but unassigned variable, and
checks $e$ against its declared type (\ruleName{assign}); the form $\exAssign{x\exAnnot{\psi}}{e}$ declares and
assigns $x$ at once (\ruleName{declare-assign}). A declaration does not check
whether its name is already declared; that check is made once for the whole scope, when the rules for function
definitions and modules introduce the variables of the scope as unbound, using the function $\scopeS(\seq{y}, s)$
(\S\ref{aux:scope}).

The conditions of \pyinline{if} and \pyinline{assert}
check against \pyinline{bool}, and an assertion message against \pyinline{str} (\ruleName{assert}, \ruleName{assert-msg}). An assertion of the literal \pyinline{False} has outcome $\Returns$, like a \pyinline{return}
(\ruleName{assert-false}, \ruleName{assert-false-msg}). A function body therefore has outcome $\Returns$ if each of its
branches ends in a \pyinline{return} or in \pyinline{assert False}, and in both module and function bodies, a
variable assigned in one branch of an \pyinline{if} is definitely assigned after the \pyinline{if} when the other
branch reaches \pyinline{assert False}, and mypy accepts both. A module whose body definitely reaches
\pyinline{assert False} is ill-formed, because the \ruleName{top-seq} and \ruleName{module} rules require outcome
$\Assigns{\Delta}$. An assertion of any other expression has outcome $\Assigns{\varnothing}$, even at type
\pyinline{Literal[False]}. Here mypy is more precise, and also treats the code after an assertion as unreachable when
the asserted expression is built from \pyinline{False} with \pyinline{not}, \pyinline{and} and
\pyinline{or}, or has the declared type \pyinline{Literal[False]}. Giving outcome $\Returns$ to every assertion at type \pyinline{Literal[False]} would accept more than mypy,
however. The expression \pyinline{(False,)[0]} synthesises \pyinline{Literal[False]}, from the type of the first
component, whereas mypy types it at \pyinline{bool} (\figref{mypy-restrictions}).

A \pyinline{match} scrutinee synthesises a type $\sigma$, and its cases $\seq{b}$ are checked in turn by the
auxiliary judgement $\Sigma; \Gamma; \zeta \vdash \tau, L, \seq{b} : S, \tau', L'$ (\specfigref{typing-cases}), which threads
a remaining type, starting from $\sigma$, and a residual $L$ of shapes, starting from the shapes of $\sigma$ (\figref{shapes}),
through the cases, merging their outcomes into $S$. The \ruleName{match} rule applies when the final remaining type is $\tyNever$, meaning the match is
exhaustive; the \ruleName{match-partial} rule applies otherwise and also merges in $\Assigns{\varnothing}$, the
outcome of the path on which the scrutinee is not matched by any of the cases.
The remaining type, the residual, reachability and exhaustiveness are the subject of
\secref{well-formedness-patterns}.

\subsubsection{Function definitions}\label{sec:well-formedness-defs}%
The \ruleName{defs} rule for a mutual def region of function definitions synthesises a type scheme for each definition
(\specfigref{typing-def}), binds all the function names of the mutual def region at the synthesised type schemes, and checks each
definition against its type scheme.
For a definition $\exDef{f[\seq{\alpha}]}{\bind{\seq{x}}{\seq{\psi}}}{\exRetAnnot{\psi}}{s}$,
the auxiliary judgements $\Sigma; \Gamma \vdash d \synth \pi$ and $\Sigma; \Gamma \vdash d \checks \pi$ synthesise the type
scheme from the annotations (\ruleName{def-signature}) and check the body $s$ (\ruleName{def-body}). Both rules extend the
context with $\TypeVar$ entries for the type parameters $\seq{\alpha}$. A type scheme without type parameters is identical to its \pyinline{Callable} type, so the \ruleName{defs} rule binds the name of a
function without type parameters as a variable of that type. The type schemes of functions with type parameters are instantiated
at a call, by the argument types (\ruleName{callee-scheme}), and when checked against a \pyinline{Callable} type, by that
type (\ruleName{var-scheme}). Since annotations denote types, not type schemes, declarations and
assignments never bind variables at type schemes, only at types.

In the body, the parameters $\seq{x}$ are bound at the types denoted by $\seq{\psi}$; variables declared or
assigned in $s$ start unbound, emulating Python's scoping of function bodies, which
prefers a locally bound name to one visible in an enclosing scope. A variable of the
enclosing scope referenced by the body must be definitely assigned at the point at which the function is defined,
whereas Python resolves the reference only when the body runs. As with any scope, the names declared in the function, including
the parameters $\seq{x}$, must be distinct from one another and from any pattern variables in $s$. The function names of the mutual def region are
declared in the enclosing scope rather than in the function, and must be distinct from the other names declared in that scope.

The body $s$ is checked with the
return type denoted by $\psi$, and must have static outcome $\Returns$ unless that type is equivalent to \pyinline{None},
so a function that declares a result definitely returns one. A return type such as $\tyUnion{\tyInt}{\tyNone}$
does not exempt the body from returning, nor permit a bare \pyinline{return}, for compatibility with mypy (\secref{mypy-restrictions}).

\subsubsection{Top-level statements}\label{sec:well-formedness-top-level}%
Top-level statements are checked by a separate
judgement, $\Sigma; q; \Gamma \vdash t : R \binding \Sigma'$ (\figref{typing-top-level}): a sequence composes in the same way as a statement sequence, a mutual type region of class
definitions and \pyinline{type} statements is a top-level form, checked by the \ruleName{types} rule, and a plain statement is checked with no return type
(\ruleName{top-stmt}), so a \pyinline{return} has no derivation at the top level.

Within a mutual type region, a \pyinline{type} statement may name any class or alias of the type region, in any
order, but a class definition may name only earlier classes and aliases, because Python~\pythonVersion{} evaluates the
field annotations and base class of a class when the class statement runs, but evaluates the body of a \pyinline{type}
statement only when the alias is first used.\footnote{\PurePy does
not support \pyinline{from __future__ import annotations}, under which Python~\pythonVersion{} defers evaluation
of annotations.} Recursive datatypes are therefore declared with their aliases before their classes, as in
\pyinline{type Expr = Num | Add} followed by definitions of \pyinline{Num} and of \pyinline{Add} with fields of type
\pyinline{Expr}. A cyclic alias such as \pyinline{type T = list[T]} has no derivation, because resolving its body
resolves the alias again.

The \ruleName{types} rule (\figref{typing-top-level}) binds the names of a mutual type region $\seq{\chi}$ and adds
its classes to the class table before checking its definitions. The context entry bound to the name declared by $\chi_i$ is $\typeEntry{\Gamma}(q, \seq{\chi}, i)$ (\S\ref{aux:type-entry}): the class
$\Type{q.c}$ if $\chi_i$ is a class definition, and the alias $\TypeAlias[\Gamma]{q}{\seq{\chi}}{i}$ if it is a \pyinline{type} statement.
The class table is extended with $\classTable{\Gamma}(q, \seq{\chi})$
(\S\ref{aux:class-table}), a class table defining all the classes of the type region. A class thus has three static forms, as a function has: the
class statement $\chi_i$, which defines it; the context entry $\Type{q.c}$, by which a variable refers to it by name; and
$\ClassDef[\Gamma]{q}{\seq{\chi}}{i}$ in the class table, the class statement together with its type region and defining
context, from which its fields and base class are read. For a function the three are the \pyinline{def} statement, the
type scheme bound to its name and the closure $\exDefClosure[\Gamma]{\rho}{\seq{d}}{i}$. Aliases and class definitions under their defining contexts carry the type region and
defining context $\Gamma$, because alias bodies, field annotations and base classes are resolved at each use rather than when the
type region is checked.
Each definition $\chi_i$ is checked under the extended class table and the context $\typeContext{\Gamma}(q, \seq{\chi}, i)$
(\S\ref{aux:type-context}), by the auxiliary judgement $\Sigma; \Gamma \vdash \chi$, which binds
every name of the type region for a \pyinline{type} statement and only the earlier names for a class definition, as above.

The judgement $\Sigma; \Gamma \vdash \chi$ checks a class definition by resolving the field annotations, which may mention the type parameters of the class, and requiring the fields it declares to be distinct and, when it extends
another class, the base class to name a class rather than an alias and to resolve to an instantiated class, and the additional fields not to repeat an inherited field
(\ruleName{class}, \ruleName{class-extend}). Class definitions also require the predefined name \pyinline{dataclass} (\figref{predefined-signatures}) to be in
scope; every \PurePy class must declare itself a dataclass. A \pyinline{type} statement $\exTypeAlias{x[\seq{\alpha}]}{\psi}$, such as \pyinline{type Pair[T] = tuple[T, T]},
declares $x$ as an alias of the type denoted by $\psi$ with the type parameters $\seq{\alpha}$ in scope
(\ruleName{type-alias}). An application of the alias such as \pyinline{Pair[int]} denotes that type at the given
arguments (\ruleName{ty-alias}), here \pyinline{tuple[int, int]}, so types never mention aliases.

\subsection{Pattern matching}
\label{sec:exhaustiveness}
\label{sec:well-formedness-patterns}

To check a \pyinline{match} with scrutinee type $\sigma$, the auxiliary judgement
$\Sigma; \Gamma; \zeta \vdash \tau, L, \seq{b} : S, \tau', L'$ (\specfigref{typing-cases}) threads a \emph{remaining type}
$\tau$ and a \emph{residual} $L$ through the cases, both over-approximations of the values of $\sigma$ which are not
matched by any of the earlier cases. The residual is an ordered set of \emph{shapes} (\figref{shapes}), each denoting a
set of values of a single type, and starts from the shapes of $\sigma$; the remaining type is coarser, a type rather
than a set of shapes, and starts from $\sigma$ itself. Two auxiliary functions narrow a type $\tau$ by a pattern $p$
(\S\ref{aux:matched-as}): $\matchedAs{\Sigma}(\Gamma, \tau, p)$ is
the type to which $\tau$ is narrowed if $p$ matches, and $\remaining{\Sigma}(\Gamma, \tau, p)$ is the type remaining if
$p$ fails. Each case's pattern is checked against the remaining type
(\secref{pattern-checking}), binding its pattern variables, and matched
against the residual (\secref{matching}). Reachability is decided by the
residual: a case is \emph{reachable} if its pattern matches at least one shape of the residual, and a match with an
unreachable case is ill-formed. For a reachable case, the body is checked under the bindings and its outcome merged
into $S$; the shapes left after matching and the type remaining if the pattern fails become the residual and remaining
type for the case that follows.

A match is \emph{exhaustive} when its cases between them match every value of $\sigma$. Exhaustiveness is decided by
the final remaining type, which the \ruleName{match} rule requires to be $\tyNever$, with \ruleName{match-partial}
applying otherwise. The remaining type thus determines exhaustiveness as well as the types of pattern variables. The Python typing
specification leaves narrowing largely unspecified,\footnote{\url{https://typing.python.org/en/latest/spec/narrowing.html}}
so the remaining type emulates the narrowing of a match scrutinee observed in mypy
(\secref{mypy-restrictions}), which subtracts a class only for a
constructor pattern that matches every value of the class, and a tuple only through one refutable component, i.e.~one whose pattern can fail to match a value of the component's type. Cases that between them cover a field of a class therefore leave an empty residual but a remaining
type other than $\tyNever$, so a function which returns from each of the cases is rejected as not always returning, and
at a class with a field of type $\tyUnion{\tyInt}{\tyNone}$ a case \pyinline{Box(n)} after a case \pyinline{Box(None)}
binds \pyinline{n} at $\tyUnion{\tyInt}{\tyNone}$ rather than at \pyinline{int}. The
usefulness algorithm for ML~\cite{maranget2007} also checks reachability and exhaustiveness with a single
relation. The residual plays the role of the term descriptions of \citet{sestoft1996}, and the uncovered
sets of \citet{karachalias2015} likewise let the type exclude cases.

The cases needed to exhaust a match therefore depend on the type of the scrutinee: a union is exhausted
by covering each disjunct, a class type by a pattern for the class itself, \pyinline{bool} by
\pyinline{True} and \pyinline{False}, and a dictionary type by the empty dictionary pattern, while \pyinline{int}, \pyinline{float}, \pyinline{str} and lists have
unboundedly many heads and need a variable or wildcard. A literal-typed scrutinee is exhausted by covering
its literals, so \pyinline{x: Literal[42] = 42} admits a match with a case for \pyinline{42} alone, while
\pyinline{x: int = 42} keeps the type open. Over
$\tyTuple{\tyBool, \tyBool}$ the cases $\patTuple{\pyinline{True}, \patWild}$,
$\patTuple{\patWild, \pyinline{False}}$ and $\patTuple{\pyinline{False}, \pyinline{True}}$ leave the empty residual,
although each covers only part of the type.

\subsection{Modules and programs}
\label{sec:well-formedness-modules}

\emph{Module checking} types a module's body and computes its signature $\Gamma$, the judgement
$\Sigma \vdash_{\mathsf{mod}} q : \Gamma \binding \Sigma'$ (\specfigref{typing-module}); it mirrors loading at run time
(\secref{operational-semantics}). The \ruleName{module} rule types the body as a top-level statement, and
the \ruleName{predefined} rule gives a predefined module the signature of
Definition~\ref{def:predefined}.
Both import forms check their target, together with its containing modules
(\figref{typing-import-prefix}). A plain import checks the root and then each module
along the chain of names, recording each as a member of its parent (\ruleName{submodules-cons}), so that the binding for the root gives attribute
access along the whole chain. Two imports with the same root, such as \pyinline{a.b} and \pyinline{a.c}, both
bind the root, and their bindings combine by \emph{context extension} $\Gamma \extend \Delta$ rather than shadow
one another. Extension is defined pointwise, like override, and combines module entries for the same module
recursively, preferring checked modules to stubs:%
\begin{specdefinition}{Extension of context entries}
\begin{defalign}
\modLoaded{q}{\Gamma} \extend \modLoaded{q}{\Gamma'} & = \modLoaded{q}{\Gamma \extend \Gamma'} \\
\modStub{q} \extend \modLoaded{q}{\Gamma} = \modLoaded{q}{\Gamma} \extend \modStub{q} & = \modLoaded{q}{\Gamma} \\
\bot \extend \theta = \theta \extend \bot & = \theta \\
\theta \extend \theta' & = \theta' \quad \text{(otherwise)}
\end{defalign}
\end{specdefinition}
\noindent A from-import also checks any imported name that denotes a submodule, and the
names it imports must be distinct. A
containing module of the target is exempt from checking if it is the importing module or one of its
containing modules (\S\ref{aux:unique-to}), because at runtime it may still be loading when the import executes. The exemption applies only to from-imports, because
for a plain import
the only containing module that could never load first is the importing module itself, and an import naming a
module contained in the importing module is excluded outright. Module checking is defined inductively, so a program with an import cycle is ill-formed. Program
well-formedness (\specfigref{typing-module}) requires the main module to be well typed and hence,
recursively, every module that the program can load; a module that is never imported is not checked.
The rule \ruleName{module} types a module body under the context of $\mathcal{P}(\pyinline{builtins})$,
overridden by the imported context and then, as in \ruleName{def-body}, by an unbound entry for each name
declared in the body or bound by a pattern in it.
The members of \pyinline{builtins} are thus in scope unqualified, and a name bound by the body
shadows a builtin throughout the module, so a use of the name before its declaration is rejected. Under mypy such a
use instead resolves to the builtin, following Python's run-time lookup. As with any scope, the names declared in the
module, including its imported names, must be distinct from one another and from any pattern variables in its
body. Since every module declares \pyinline{__name__} (\secref{modules-programs}), a module is ill-formed if its body
declares that name again, imports it, or binds it in a pattern.

\input{spec/fig/typing-module}

The signature $\Gamma$ produced by module checking (\specfigref{typing-module}) comprises the classes, type aliases
and variables defined by a module, together with its intrinsic \pyinline{__name__} and a stub for each submodule,
but not the names that it imports: following PEP 484\footnote{\url{https://peps.python.org/pep-0484/}}, an imported
name is a private dependency, not re-exported as part of the interface. Submodule stubs and the bindings of the module
body are disjoint, because the module rules exclude a module that binds a name that is also the name of
a submodule.

\section{Types}
\label{sec:types}

The typing judgement gives each expression a type. It is intended as a refinement of mypy's: a well-typed
\PurePy program should be accepted by mypy, and \PurePy may reject programs mypy accepts but not the
reverse. The entry for a definitely assigned variable is its type
(Definition~\ref{def:context}), so \ruleName{var} applies whenever $\Gamma(x)$ is a type, and a variable
bound to $\statusNotDefAssigned$ has no rule. Every parameter, return and assignment carries an annotation, so the type of a definition is given rather
than inferred from its body; within an expression, typing is bidirectional.
\emph{Synthesis} $\Gamma \vdash e \synth \tau$ reads a type out of an expression (\figrefTwo{typing-synth}{typing-synth-ctd}),
and \emph{checking} $\Gamma \vdash e \checks \tau$ tests an expression against a type supplied by its
surroundings (\figref{typing-check}).

Variables, literals, attribute references, calls, constructor calls, operators and subscripts synthesise. A
literal $\ell$ synthesises the literal type $\tyLiteral{\ell}$, whose \emph{base type} is $\widen(\ell)$:
\begin{defalign}
\widen(n) & = \tyInt \quad \text{($n$ an integer literal)} \\
\widen(n) & = \tyFloat \quad \text{($n$ a float literal)} \\
\widen(w) & = \tyStr \\
\widen(\pyinline{True}) = \widen(\pyinline{False}) & = \tyBool \\
\widen(\pyinline{None}) & = \tyNone
\end{defalign}

\noindent The \emph{alternatives} of a type are the sequence of a union's operands, and the type itself
otherwise. Two types are \emph{comparable} when either is a subtype of the other. Subtyping and the definitions
below depend on the context, since a class is below its ancestors, and $\Gamma$ is left implicit where it
plays no part. Two comparable types
\emph{join} to the larger type and two incomparable types to their union. A sequence of types joins by
joining the first with the join of the rest:
\begin{defalign}
\membersOf(\tyUnion{\sigma}{\tau}) & = \membersOf(\sigma) \mathbin{\concat} \membersOf(\tau) \\
\membersOf(\tau) & = \tau \quad \text{(otherwise)} \\[3mm]
\joinTy(\sigma, \tau) & = \tau \quad \text{if } \Gamma \vdash \sigma \subty \tau \\
\joinTy(\sigma, \tau) & = \sigma \quad \text{if } \Gamma \vdash \tau \subty \sigma \\
\joinTy(\sigma, \tau) & = \tyUnion{\sigma}{\tau} \quad (\text{otherwise}) \\
\joinTy(\tau) & = \tau \\
\joinTy(\tau_1, \seq{\tau}) & = \joinTy(\tau_1, \joinTy(\seq{\tau}))
\end{defalign}

\noindent So joining a type with itself gives that type, joining a class with one of its ancestors gives the ancestor, and
joining \pyinline{int} with \pyinline{str} gives $\tyUnion{\tyInt}{\tyStr}$.

A class entry $\clsEntry{\Gamma}{q.c}{\bind{\seq{x}}{\seq{\tau}}}{c'}$ records the declared
type of each field it introduces, and $\fields(C)$ is the bindings of all its fields, those of the base
class first. A constructor call $\exConstr{q}{a}$ pairs each argument with a field using
$\fieldMap$, checks it against that field's type, and synthesises $q$ as a class type (\ruleName{constr}). In an attribute reference $\exAttr{e}{x}$ the object $e$ must synthesise a class $q$, and
$\exAttr{e}{x}$ then has the type bound to $x$ in $\fields(C)$, for the entry $C$ that $q$ resolves to
(\ruleName{attr-object}). Each binary operator has a signature $\odot : (\sigma, \sigma') \to \tau$ and each unary operator a
signature $\ominus : \sigma \to \tau$, relating operand types to result type
(\figref{operator-signatures}). A
signature with type variables stands for all its instances, which agree on the result type.
Where several signatures apply, the first listed is used, so \pyinline{1 + 2}
is an \pyinline{int} and \pyinline{1 + 2.0} a \pyinline{float}. In a subscript $\exSubscript{e}{e'}$ there is a rule for each container $e$ can synthesise: a list
(\ruleName{subscript-list}) or string (\ruleName{subscript-str}) with $e'$ of type \pyinline{int}, and a
dictionary with $e'$ of type \pyinline{str} (\ruleName{subscript-dict}). Tuples have three rules: an index
that synthesises a literal type gives the component type at that position, counting from the end where the index
is negative (\ruleName{subscript-tuple}, \ruleName{subscript-tuple-neg}), and any other index of type
\pyinline{int} gives the union of the component types (\ruleName{subscript-tuple-int}). A negated numeric
literal synthesises the negated literal type (\ruleName{unop-literal}), and \ruleName{unop} excludes that
form, to keep the judgement deterministic.

Lambdas check, as do lists, tuples, dictionaries and comprehensions. Their types are not determined by
the expression alone: $\exList{}$ is a list of any element type, and a lambda's parameters cannot be annotated in
Python, so both take their type from the surroundings. An expression that synthesises $\sigma$ checks against any supertype
of $\sigma$ (\ruleName{check-synth}), which applies only where no other rule does, so both judgements are
syntax-directed and an expression has at most one derivation in each.

The division follows the usual recipe for bidirectional systems~\cite{davies2000,dunfield2021}: introduction forms
check, since a lambda or an empty list does not determine its own type, and elimination forms synthesise,
since a call, a subscript or an attribute reference starts from a subterm whose type is known. Type systems that
follow the recipe strictly usually rely on an annotation form $(e \mathbin{:} \tau)$, which synthesises by
construction, so a checking form written with an annotation can be used in any context where synthesis is required. Python has no such form, allowing annotations only on
parameters, returns and assignments. \PurePy instead gives the introduction forms synthesis rules of their own
wherever their parts determine the type, following Swift, Kotlin and
Scala~\cite{swift2025,kotlin2025,odersky2025}: a tuple when all its components synthesise, a
comprehension when its body synthesises, and a non-empty list or dictionary when at least one element
synthesises, the others checking against the join of the types of those that synthesise (\ruleName{syn-list}, \ruleName{syn-tuple},
\ruleName{syn-dict}, \ruleName{syn-list-comp}, \ruleName{syn-dict-comp}). Each of these forms keeps its checking rule as well. An empty list or dictionary and a lambda have no
synthesis rule at all, so checking is the only way to type them. A non-empty list has both, and the
checking rule is still needed where the expected element type is wider than the one the elements
synthesise, since \pyinline{list} is invariant.

Subtyping (\figref{subtyping}) is reflexivity, a literal type below its base type, and a class below its
ancestors, with \pyinline{object} above every type and \pyinline{Never} below every type. A union is above
each of its members and below every type that is above all of them. Lists, dictionaries, tuples and
callables are related only by reflexivity, since \pyinline{list} and \pyinline{dict} are invariant in mypy
and covariance would accept programs mypy rejects. An \pyinline{int} is a \pyinline{float}, as PEP~484
requires, so \pyinline{x: float = 0} is well typed. A \pyinline{bool} is not an \pyinline{int}, though
Python treats it as one.

A generator draws its bindings from the elements of a value, and $\elemTy$ gives the type of those elements,
mirroring $\iterOp$ (\secref{auxiliary-values}):
\begin{defalign}
\elemTy(\tyList{\tau}) & = \tau \\
\elemTy(\tyStr) & = \tyStr \\
\elemTy(\tyDict{\tau}) & = \tyStr \\
\elemTy(\tyTuple{\tau, \ldots, \tau}) & = \tau
\end{defalign}

\noindent A tuple whose component types differ has no element type, so it cannot be iterated.

Statements carry the return type of the function they appear in as a second argument to the left of the
turnstile: $\Gamma; \tau \vdash t : R$ says that $t$ has result type $R$ in $\Gamma$, in a
function declared to return $\tau$ (\figref{typing-stmt}). The type $\tau$ is an obligation on the
\pyinline{return} statements within $t$ rather than a property of $t$, so every rule passes it down
unchanged. A \pyinline{return} checks its expression against $\tau$, and a bare
\pyinline{return} requires $\tau$ to admit \pyinline{None}. An assignment takes its type from its
annotation and checks the expression against it; the conditions of \pyinline{if} and \pyinline{assert}
check against \pyinline{bool}, and an assertion message against \pyinline{str}.

A function definition binds its parameters at their annotated types and its own name, and the names of the
region it belongs to, at the corresponding $\pyinline{Callable}$ type; the variables the body assigns start
at $\statusNotDefAssigned$, as they do without types (\ruleName{def}). The body is checked with the
declared return type, and must have result type $\Returns$ unless the function returns \pyinline{None},
so a function that declares a result definitely returns one.

A \pyinline{match} scrutinee synthesises a type, and each pattern checks against it, binding its variables at
the types of the positions they match (\figref{typing-pat}). A constructor pattern requires its class to be
a subtype of the scrutinee's type, so a case that cannot match is rejected rather than being merely
unreachable.

Reachability and exhaustiveness are the two halves of one computation (\figref{coverage}). A \emph{shape}
$k$ denotes a set of values: $\shapeAny{\tau}{N}$ is a value of type $\tau$ whose head is none of $N$,
where $N$ collects literals, class names and sequence lengths, and the remaining forms are a literal, a
constructor, a tuple and a list, each with shapes in place of sub-patterns. The \emph{residual} of the
scrutinee's type is one shape per alternative of it, and $\splitShape$ divides a set of shapes into the
part a pattern matches and the part it leaves.

The cases are then walked once, from the residual of the scrutinee's type, in the same shape as
$\dispatch$ walks them at run time (\figref{typing-cases}). Each case checks its pattern, checks its body
under the bindings, and must match some shape of the residual, which is what makes it reachable, and the
part it leaves is passed on. \ruleName{match}
applies where the walk ends with an empty residual, and \ruleName{match-partial} where it does not, merging
in $\Assigns{\varnothing}$ for the values that fall through. A union is exhausted
by covering each member, a class type by a pattern for the class itself, and \pyinline{bool} by
\pyinline{True} and \pyinline{False}, while \pyinline{int}, \pyinline{str}, lists and dictionaries have
unboundedly many heads and need a variable or wildcard. Splitting is strictly sharper than comparing
patterns pairwise: over $\tyTuple{\tyBool, \tyBool}$ the cases $\patTuple{\pyinline{True}, \patWild}$,
$\patTuple{\patWild, \pyinline{False}}$ and $\patTuple{\pyinline{False}, \pyinline{True}}$ are
exhaustive, though no one of them subsumes what a further case would match.

Merging two branches merges their contexts pointwise. A variable definitely assigned in both, at $\tau$ and
$\tau'$, is of type $\joinTy(\tau, \tau')$, and a variable definitely assigned in one branch alone is
$\statusNotDefAssigned$.

\begin{lemma}[Transitivity of subtyping]
\label{lem:subtyping-transitive}
If $\Gamma \vdash \sigma \subty \tau$ and $\Gamma \vdash \tau \subty \upsilon$ then $\Gamma \vdash
\sigma \subty \upsilon$.
\end{lemma}

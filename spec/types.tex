\section{Types}
\label{sec:types}

The typing rules say whether a program is well typed. They are intended as a refinement of mypy's: a well-typed
\PurePy program should be accepted by mypy, and \PurePy may reject programs mypy accepts but not the
reverse. Function signatures, assignments and dataclass fields are annotated with type expressions, and a
type expression denotes a type under a context (\figref{resolve-type}). Every parameter and return carries
one, so the type of a definition is given rather than inferred from its body. A class name resolves to a
class entry and every other name must resolve to a predefined entry (\figref{predefined-types}).

The context entry for a definitely assigned variable is its type (Definition~\ref{def:context}), and a variable
that is not definitely assigned is bound to $\statusNotDefAssigned$. Two contexts from different branches of a conditional merge pointwise. A variable definitely assigned in both, at $\sigma$ and $\tau$, is of type
$\joinTy(\sigma, \tau)$, whereas a variable definitely assigned in one branch alone is
$\statusNotDefAssigned$.

\subsection{Subtyping}
\label{sec:subtyping}

The \emph{base type} of a literal $\ell$ is $\widen(\ell)$, and of a type is that type with a literal
type replaced by the base type of its literal (\secref{types-auxiliary}).

Subtyping (\figref{subtyping}) has every type below itself, a literal type below its base type, and a class below its
ancestors, with \pyinline{object} above every type and \pyinline{Never} below every type. A union is above
each of its members and below every type that is above all of them. A tuple type is covariant, below another of the
same length whose components are above its own. Lists, dictionaries and callables
are related only by reflexivity, since \pyinline{list} and \pyinline{dict} are invariant in mypy and
covariance would accept programs mypy rejects. The types with a length, namely lists, dictionaries,
strings and tuples, are below \pyinline{Sized}. An \pyinline{int} is a \pyinline{float}, as PEP~484
requires, so \pyinline{x: float = 0} is well typed. A \pyinline{bool} is not an \pyinline{int}, although
Python treats it as one.

\begin{lemma}[Transitivity of subtyping]
\label{lem:subtyping-transitive}
If $\Gamma \vdash \sigma \subty \tau$ and $\Gamma \vdash \tau \subty \tau'$ then $\Gamma \vdash
\sigma \subty \tau'$.
\end{lemma}

Two types are \emph{comparable}
when either is a subtype of the other. Two comparable types
\emph{join} to the larger type and two incomparable types to their union. A sequence of types joins by
joining the first with the join of the rest, with \pyinline{Never} as the unit (\secref{types-auxiliary}).
So joining a type with itself gives that type, joining a class with one of its ancestors gives the ancestor, and
joining \pyinline{int} with \pyinline{str} gives $\tyUnion{\tyInt}{\tyStr}$.

\subsection{Expression typing}
\label{sec:expression-typing}

Within an expression the typing judgement gives each subexpression a type, and
is bidirectional. \emph{Synthesis} $\Gamma \vdash e \synth \tau$ reads a type out of an expression (\figrefTwo{typing-synth}{typing-synth-ctd}),
and \emph{checking} $\Gamma \vdash e \checks \tau$ tests an expression against a type supplied by its
surroundings (\figref{typing-check}). The division follows the usual recipe for bidirectional
systems~\cite{davies2000,dunfield2021}: introduction forms check, since a lambda or an empty list does not
determine its own type, and elimination forms synthesise, since a call, a subscript or an attribute
reference starts from a subterm whose type is known. Type systems that follow the recipe strictly usually
rely on an annotation form $(e \mathbin{:} \tau)$, which synthesises by construction, so a checking form
written with an annotation can be used in any context where synthesis is required. Python has no such form,
allowing annotations only on parameters, returns and assignments, so \PurePy gives the introduction forms
synthesis rules of their own wherever their parts determine the type, following Swift, Kotlin and
Scala~\cite{swift2025,kotlin2025,odersky2025}.

Variables, literals, attribute references, calls, constructor calls, operators and subscripts synthesise.
The \ruleName{var} rule applies whenever $\Gamma(x)$ is a type, so a variable that is not definitely
assigned has no rule. A
literal $\ell$ synthesises the literal type $\tyLiteral{\ell}$.

A class entry $\clsEntry{\Gamma}{q.c}{\bind{\seq{x}}{\seq{\tau}}}{c'}$ records the declared
type of each field it introduces, and $\fields(C)$ is the bindings of all its fields, those of the base
class first. A constructor call $\exConstr{q}{a}$ pairs each argument with a field using
$\fieldMap$, checks it against that field's type, and synthesises the class entry $C$ that $q$ resolves to,
which is the class type (\ruleName{constr}). In an attribute reference $\exAttr{e}{x}$ the object $e$ must
synthesise a class entry $C$, and $\exAttr{e}{x}$ then has the type bound to $x$ in $\fields(C)$
(\ruleName{attr-object}). Typing a program refines the signature of a predefined module
(Definition~\ref{def:predefined}), binding $\pymath{\_\_name\_\_}$ at $\tyStr$ and each member at the entry
listed for it in \figref{predefined-types}, so \pyinline{len} takes a \pyinline{Sized} and \pyinline{print}
one argument of any type, while \pyinline{Callable} and the other three names that no expression may
mention keep the entry $\predefName$. Each binary operator has a signature $\odot : (\sigma, \sigma') \to \tau$ and each unary operator a
signature $\ominus : \sigma \to \tau$, relating operand types to result type
(\figref{operator-signatures}). A
signature with type variables stands for all its instances, which agree on the result type; a variable binds
the operand's type as it is, and an operand type written out is matched by any subtype of it. Where several
signatures give a result the first listed is used, so \pyinline{1 + 2} is an \pyinline{int} and
\pyinline{1 + 2.0} a \pyinline{float}. Equality is available on \emph{equality types}, which are the types
whose values structural equality relates:
\begin{defalign}
\Gamma \vdash \nu \eqType \\
\Gamma \vdash \tyLiteral{\ell} \eqType \\
\Gamma \vdash \tyList{\tau} \eqType \quad & \text{if } \Gamma \vdash \tau \eqType \\
\Gamma \vdash \tyDict{\tau} \eqType \quad & \text{if } \Gamma \vdash \tau \eqType \\
\Gamma \vdash \tyTuple{\seq{\tau}} \eqType \quad & \text{if } \Gamma \vdash \tau_i \eqType \quad (\forall i) \\
\Gamma \vdash \tyUnion{\sigma}{\tau} \eqType \quad & \text{if } \Gamma \vdash \sigma \eqType \text{ and } \Gamma \vdash \tau \eqType \\
\Gamma \vdash q \eqType \quad & \text{if } \Gamma \vdash q : C \text{ and } \Gamma \vdash \tau \eqType \text{ for each } \bind{x}{\tau} \in \fields(C)
\end{defalign}

\noindent A callable type is not an equality type, and neither is any type with a callable component, so
comparing two functions is rejected rather than left undefined. \emph{Resolution} looks the operator up at the operand types, and
at their base types where no signature gives a result for the operand types themselves
(\secref{types-auxiliary}). The second clause lets \pyinline{1 == 0} use the equality signature at \pyinline{int}, since two
distinct literal types are not comparable. Taking the operand types as they are first keeps \pyinline{2 **
3} an \pyinline{int}, since the exponent binds a variable that its base type would not. Resolution is more
precise than mypy for this operator, whose overloads give \pyinline{Any} as soon as the exponent is not a
literal, where resolution gives \pyinline{float}.

In a subscript $\exSubscript{e}{e'}$ there is a rule for each container $e$ can synthesise: a list
(\ruleName{subscript-list}) or string (\ruleName{subscript-str}) with $e'$ of type \pyinline{int}, and a
dictionary with $e'$ of type \pyinline{str} (\ruleName{subscript-dict}). Tuples have three rules: an index
that synthesises a literal type gives the component type at that position, counting from the end where the index
is negative (\ruleName{subscript-tuple}, \ruleName{subscript-tuple-neg}), and any other index of type
\pyinline{int} gives the union of the component types (\ruleName{subscript-tuple-int}). A negated numeric
literal synthesises the negated literal type (\ruleName{unop-literal}), and \ruleName{unop} excludes that
form, to keep the judgement deterministic.

Lambdas check, as do lists, tuples, dictionaries and comprehensions. Their types are not determined by
the expression alone: $\exList{}$ is a list of any element type, and a lambda's parameters cannot be annotated in
Python, so both take their type from the surroundings. An expression that synthesises $\sigma$ checks against any supertype
of $\sigma$ (\ruleName{check-synth}), which applies only where no other rule does, so both judgements are
syntax-directed and an expression has at most one derivation in each.

The forms with synthesis rules of their own are a tuple when all its components synthesise, a
comprehension when its body synthesises, and a non-empty list or dictionary when at least one element
synthesises, the others checking against the join of the base types of those that synthesise (\ruleName{syn-list},
\ruleName{syn-tuple}, \ruleName{syn-dict}, \ruleName{syn-list-comp}, \ruleName{syn-dict-comp}). A list,
dictionary or comprehension takes the base type of what its elements or body synthesise, since
\pyinline{list} and \pyinline{dict} are invariant and a literal element type would keep the container from
matching any other. Each of these forms keeps its checking rule as well. An empty list or dictionary and a lambda have no
synthesis rule at all, so checking is the only way to type them. A lambda applied to arguments is the
exception, since the arguments give the parameter types, and the call then synthesises the type of the body
or checks the body against an expected type (\ruleName{syn-call-lambda}, \ruleName{call-lambda}). A
comprehension uses that form to pass a generator variable to a lambda by value, which it may not capture. A non-empty list has both, and the
checking rule is still needed where the expected element type is wider than the one the elements
synthesise, since \pyinline{list} is invariant.

Typing a comprehension types its qualifiers, which bind the variables its body may use
(\figref{typing-check}). A generator draws those bindings from the elements of a value, and $\elemTy$ gives
the type of those elements (\secref{types-auxiliary}), mirroring $\iterOp$ (\secref{auxiliary-values}). A
tuple is iterated at the join of the base types of its components, whether or not they agree.
A type with no clause, such as a class or a callable, cannot be iterated, and a generator over a value of
that type has no rule.

\subsection{Statement typing}
\label{sec:statement-typing}

Statements carry the return type of the function they appear in as a second argument to the left of the
turnstile: $\Gamma; \tau \vdash t : R$ says that $t$ has result type $R$ in $\Gamma$, in a
function declared to return $\tau$ (\figref{typing-stmt}). The type $\tau$ is an obligation on the
\pyinline{return} statements within $t$ rather than a property of $t$, so every rule passes it down
unchanged. A \pyinline{return} checks its expression against $\tau$, and a bare
\pyinline{return} requires \pyinline{None} to be a subtype of $\tau$. An annotated assignment takes its type
from the annotation and checks the expression against it, and an unannotated assignment takes the type the
expression synthesises (\ruleName{assign}, \ruleName{assign-unannot}). The conditions of \pyinline{if} and \pyinline{assert}
check against \pyinline{bool}, and an assertion message against \pyinline{str}. A class declaration binds
the class name to its entry, requiring that name to be unbound and the class's own fields to be distinct,
and, where it extends another class, that class to be bound and the own fields not to repeat an inherited
one (\ruleName{class}, \ruleName{class-extend}). It also requires \pyinline{dataclass} to be in scope, since
the declaration names it. Each rule that takes an annotation resolves it to a type
(\figref{resolve-type}).

A function definition binds its parameters at their annotated types and its own name, and the names of the
mutual region it belongs to, at the corresponding $\pyinline{Callable}$ type; variables assigned in the body start
at $\statusNotDefAssigned$ (\ruleName{def}). The body is checked with the
declared return type, and must have result type $\Returns$ unless the function returns \pyinline{None},
so a function that declares a result definitely returns one.

A \pyinline{match} scrutinee synthesises a type. Both \pyinline{match} rules hand the cases to the
judgement $\Gamma; \tau; L \vdash \seq{h} : S, L'$, which takes them in turn,
requiring each to match something and the whole list to exhaust the type. The \emph{residual} $L$ holds the
values no earlier case has matched, and $L'$ those still unmatched once these cases are done. The judgement
starts from $\shapesOf(\widen(\sigma), \varnothing)$, which denotes every value of the scrutinee's base
type. Taking the base type keeps a literal case from exhausting the scrutinee on its own, so a
\pyinline{match} on \pyinline{42} with a case for \pyinline{42} still admits a catch-all. Each case matches its
pattern against the residual (\secref{exhaustiveness}), which yields the bindings the pattern makes as
well as the values it leaves. The body is then checked under those bindings.

\subsection{Exhaustiveness checking}
\label{sec:exhaustiveness}

\input{spec/fig/metavariables-types}

\input{spec/fig/syntax-shapes}

Reachability and exhaustiveness are the two halves of one computation
(\figrefTwo{shapes}{pat}), as in the usefulness algorithm for
ML~\cite{maranget2007} and in the term descriptions a match compiler carries~\cite{sestoft1996}. Matching a
pattern against a shape takes the scrutinee's type into account, as the uncovered sets of
\citet{karachalias2015} do. A \emph{shape} $k$
denotes a set of values of a type, written $\Gamma \vdash k : \tau$. Every shape has a least such type,
$\shapeTy(k)$ (\secref{types-auxiliary}). The form $\shapeAny{\tau}{N}$ is a
value of type $\tau$ whose outermost head is not among those in $N$, where $N$ \emph{constructs} $\tau$: its
elements are subclasses where the type is a class, lengths where it is a list, and literals below the type
otherwise (\figref{shapes}). The other forms are a literal, a constructor, a tuple, a list and a dictionary, each with shapes in place of
sub-patterns. A list shape records its element type as well, which the element shapes do not determine. The shapes of $\tau$ that remain once the heads in $N$ are excluded are
$\shapesOf(\tau, N)$: one shape per member of a union, and none at all where $N$ exhausts $\tau$. No shape
carries a union type, since $\shapesOf$ is the only source of the form $\shapeAny{\tau}{N}$ and it splits a
union into its members. The
matching judgement $\Gamma \vdash L, p \matches K, L' \binding \Delta$ divides a set of shapes into the
matched shapes $K$ and the \emph{residual} $L'$, binding $\Delta$, one shape at a time and one position at a time
(\figrefTwo{pat}{pat-rows}). A pattern that cannot match a shape has no derivation against it, so
\ruleName{pat-shapes} takes the shapes it does match, which must not be none, and passes the others into
the residual untouched. A variable pattern binds at $\shapeTy(k)$ for the shape $k$ it matches, and a
pattern named by \pyinline{as} at the join over the shapes it matched, so a case for one alternative of a
union leaves a later variable case bound at the others alone. Bindings from the positions of a row, or from
the keys of a dictionary pattern, compose by disjoint union, so a pattern that binds a name twice has no
derivation.

The cases are then walked once, from $\shapesOf(\widen(\sigma), \varnothing)$ for the scrutinee's type $\sigma$, in the same shape as
$\dispatch$ walks them at run time (\figref{typing-cases}). Each case matches its pattern against the residual, checks its
body under the bindings that matching gives, and passes on the residual it leaves. A case that matches nothing is
rejected, whether because the scrutinee can never take that shape or because the earlier cases already cover it. \ruleName{match}
applies where the walk ends with an empty residual, and \ruleName{match-partial} where it does not, merging
in $\Assigns{\varnothing}$ for the values that fall through. A union is exhausted
by covering each member, a class type by a pattern for the class itself, and \pyinline{bool} by
\pyinline{True} and \pyinline{False}, while \pyinline{int}, \pyinline{str} and lists have
unboundedly many heads and need a variable or wildcard. A dictionary shape has a form of its own,
$\shapeDict{\tau}{\beta}{N}$, standing for dictionaries that hold each key of $\beta$ with a value of the
shape $\beta$ gives it, and hold no key of $N$. A dictionary pattern is taken one key at a time, no key twice
(\ruleName{pat-dict-bound}, \ruleName{pat-dict-unbound}). A key already in $\beta$ is matched against the
shape recorded for it, and a key in neither $\beta$ nor $N$ against the value type, adding to the residual the
dictionaries that lack the key. The empty pattern matches every dictionary and leaves nothing, so it alone
exhausts a dictionary type (\ruleName{pat-dict-nil}). Exhaustiveness need not come from a catch-all: over
$\tyTuple{\tyBool, \tyBool}$ the cases $\patTuple{\pyinline{True}, \patWild}$,
$\patTuple{\patWild, \pyinline{False}}$ and $\patTuple{\pyinline{False}, \pyinline{True}}$ leave nothing,
although each covers only part of the type.
